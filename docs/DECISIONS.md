# 設計判断の記録

新しい判断をしたら、下に追記します。番号は振り直しません。判断を覆したときは、元の項目は消さずに「→ D-xxx で変更」と書き足します。

| # | 日付 | 判断 | 理由・根拠 |
|---|---|---|---|
| D-001 | 2026-10-30 | AI からは MCP ツール、人からは WebUI を使う。どちらも同じブローカーの同じデータを見る | 仕様書 §1。画面の操作に頼る連携は採らない |
| D-002 | 2026-10-30 | 通知では「未取得がある」ことだけを伝え、本文は DB を正として `channel_receive` で取りに来させる | 仕様書 §8。Claude の Channel には ACK がなく、届かなかった通知は黙って捨てられるため、本文を通知に載せない |
| D-003 | 2026-10-30 | Codex への通知は `codex queue`、Claude への通知は Channel（`notifications/claude/channel`）で行う | 仕様書 §10。PoC で、実物の CLI で動くことを確認（[記録](verification/poc-20261031.md)） |
| D-004 | 2026-10-30 | 承認をメッセージで中継しない（`claude/channel/permission` を宣言しない） | 仕様書 §9。PoC で、メッセージでは承認されないことを確認（I3） |
| D-005 | 2026-10-31 | 本実装の前に PoC で受信経路を確かめ、合格してから本実装に入る | 受信経路が動かなければ設計を作り直すことになるため（ユーザーの提案）。G1〜G5 すべて合格 |
| D-006 | 2026-10-31 | 受信済み・ACK 待ちのメッセージでは、もう一度通知しない | PoC で余分な通知と空のターンが出たため |
| D-007 | 2026-10-31 | Codex には時間ごとの再通知をしない。Claude は 5 分・15 分・30 分 | queue は Codex 側に保存され、アイドルになれば1件につき1ターン処理される。重ねると余分なターンになる（実機で確認） |
| D-008 | 2026-10-31 | 通知文に、受信・ACK・返信の最小限の手順を入れる | Codex では MCP の instructions がツールの説明としてしか渡らず、PoC で依頼に返信しなかった。通知文に入れたら返信した |
| D-009 | 2026-10-31 | SQLite は Node 組み込みの `node:sqlite` を使う | ネイティブ部品が不要で、Windows でのインストール失敗を避けられる |
| D-010 | 2026-10-31 | 接続状態（最後のハートビート）はメモリで管理し、状態が変わったときだけ DB に書く | 5 秒ごとの書き込み（fsync）を避けるため。ブローカーを再起動すると全員 offline から始まる |
| D-011 | 2026-10-31 | WebUI（閲覧専用）を LAN の 47822 にも公開する（既定で有効）。AI 用・管理用の API は 127.0.0.1 のみ | 別の PC から見守りたいというユーザーの要望。閲覧に必要な API 以外は LAN 側に置かない |
| D-012 | 2026-10-31 | 会話の中で `channel_join` を呼ぶだけで参加できるようにする（参加用キー）。トークンファイルの方法も残す | ユーザーの要望：「ふつうの MCP として登録し、引数を付けて起動すればいい」。専用の起動コマンドは作らない |
| D-013 | 2026-10-31 | Codex の会話 ID は、AI が `$CODEX_THREAD_ID` を調べて `channel_join` で渡す | Codex は MCP サーバーに会話 ID を渡さないが、シェルには渡す（実機で確認） |
| D-014 | 2026-10-31 | 通信の仕組みは全員対等（ピアツーピアのメッセージバス）とし、統括を立てる運用は使い方の例として位置づける | 仕様書 §要件「通信経路を統括の中継に限定しない」。統括中心の仕組み（仕事の管理・権限）は今後の検討（ROADMAP） |
| D-015 | 2026-10-31 | ドキュメントは「現行」と「履歴（`docs/archive/`）」に分け、食い違いはコードを正とする | 新しいセッションが古い設計を信じて誤った作業をしないようにするため |
