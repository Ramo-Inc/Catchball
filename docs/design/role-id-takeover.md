# 仕様：役割の ID で参加し、担当のハーネスを入れ替えられるようにする

- 状態：**合意済み・未実装**（2026-11-02、ユーザーとの質疑で決定。同日、コードとの突き合わせのレビューを反映）
- 対象のバージョン：v1.0.0-alpha.1 の次
- 前提となる決定事項は [role-id-takeover-decisions.md](role-id-takeover-decisions.md)。この仕様書は、その決定を実装に落としたもの
- 実装が終わったら、この文書の状態を「実装済み」にし、内容を ARCHITECTURE・OPERATIONS・MCP_TOOLS・DECISIONS に反映する

## 1. 困っていること

- **ID がハーネスに縛られている**
  - 参加者の ID が、Codex か Claude か（ハーネス）に縛られています。
  - 「開発担当を Codex から Claude Code に替えたい」ときに、同じ ID では参加できません。ブローカーが「この ID は codex 用です」と断ります。
- **入れ替えると、受信箱が引き継げない**：別の ID で参加し直すと別人の扱いになり、前の担当宛てで、まだ受け取っていないメッセージを受け取れません。
- **自動の ID がハーネス名になる**
  - ID を省略すると `codex-1`・`claude-2` のような ID が自動で付きます。
  - そのため、統括や担当がハーネスの名前で相手を呼ぶことになり、担当の中身を替えると呼び方が古くなります。

## 2. 解決のしかた

- **参加者は、`dev`・`planning`・`review` のような役割の ID だけで識別する。** Codex か Claude かは、そのとき参加しているセッションの属性にすぎない。
- **その ID を使っているセッションがいなければ、どのハーネスからでも参加できる**：使っていない状態とは、切断中・退出済み・未参加のどれかです。ユーザーは新しいセッションに「キャッチボールに ID は dev で参加して」と頼むだけです。
- **未取得のメッセージは引き継がれる**：まだ受け取っていないメッセージは ID にひも付いているので、新しく参加したセッションがそのまま受け取れる。
- **ID は必ず指定する**：省略したら断り、「ID は自分で決めず、ユーザーに尋ねる」ように案内する。
- **ID が使用中なら断る**：別の ID に逃げさせず、「前のセッションが終了したかユーザーに確認してもらう」ように案内する。
- **入れ替わりは自動で知らせない**：引き継ぎ（作業の状況や経緯）は、セッションどうしで行う。
- **仕組みは増やさない**：固まったセッションの強制切断などは作らない。異常時の見分け方と対処は、運用の文書にまとめる。

## 3. ユーザーストーリー

**担当の入れ替え**
1. ユーザーとして、開発担当を Codex から Claude Code に替えたい。担当を、そのとき使いやすいほうの AI で続けたいから。
2. ユーザーとして、新しいセッションに「ID は dev で参加して」と頼むだけで入れ替えたい。特別な操作や設定の書き換えをしたくないから。
3. ユーザーとして、Claude Code から Codex へも同じように入れ替えたい。どちらの向きでも同じ手順にしたいから。
4. ユーザーとして、前の担当宛てで、まだ受け取っていないメッセージを新しい担当に受け取らせたい。統括に依頼を送り直させたくないから。
5. ユーザーとして、入れ替えのあとも、統括が今までどおり `dev` 宛てに送れるようにしたい。統括に宛先の変更を教えたくないから。
6. 統括として、相手の中身が替わっても、同じ `dev` に依頼を送り続けたい。宛先を担当の役割で覚えておけばよいから。
7. ユーザーとして、同じハーネスの新しい会話（Codex の新しいスレッドなど）でも、同じ ID で参加し直したい。会話が長くなったときに新しい会話で続けたいから。
8. 新しく参加した担当として、自動受信の確認がやり直されてほしい。新しいセッションに通知が届くことを確かめたいから。
9. 新しく参加した Claude の担当として、前の Codex の会話 ID が残っていても、正しく Channel で知らせを受けたい。
10. 新しく参加した Codex の担当として、自分の会話 ID（`$CODEX_THREAD_ID`）で知らせを受けたい。前の会話に知らせが届いても意味がないから。
11. ユーザーとして、入れ替えたあとに前のセッションが万一戻ってきても、メッセージを送ったり受け取ったりできないようにしたい。同じ担当が2人になって混乱しないように。
12. ユーザーとして、統括の役目を持った ID（例：`main`）を入れ替えても、統括のままでいてほしい。統括の役目は ID に付いているものだから。
13. ユーザーとして、入れ替わったことを、ほかの参加者へ自動で知らせないでほしい。知らせが増えるだけで、引き継ぎはセッションどうしでやればよいから。
14. ユーザーとして、Codex → Claude → Codex と入れ替えたときや、Codex の新しい会話で参加し直したときに、通知が前の会話に届かないでほしい。今のセッションだけに届けたいから。

**ID の指定**
15. ユーザーとして、ID を必ず自分で決めたい。担当を役割で呼び分けたいから。
16. AI として、ID を指定せずに参加しようとしたら、どの ID で参加するかユーザーに尋ねるよう案内されたい。勝手に ID を作って、決まりを崩さないように。
17. ユーザーとして、AI が ID を省略して参加しようとしたら、参加させないでほしい。`codex-1` のような ID が勝手に増えないように。
18. ユーザーとして、すでに参加済みのセッションが別の ID を指定したら、断ってほしい。AI が「別の ID で参加した」と思い込まないように。
19. ユーザーとして、今使っている `codex-main` や `claude-1` のような ID は、そのまま使い続けたい。今の DB やセッションを作り直したくないから。
20. ユーザーとして、ID の付け方（役割で付け、ハーネスでは付けない）を説明した文書を読みたい。初めての人やセッションにも同じ決まりで使わせたいから。

**ID が使用中のとき**
21. AI として、使用中の ID で参加しようとしたら、別の ID に逃げず、ユーザーに確認してもらうよう案内されたい。担当が2つの ID に分かれないように。
22. ユーザーとして、ID が使用中と言われたときに、前のセッションがまだ動いているのか、固まっているのかを見分けたい。
23. ユーザーとして、前のセッションが完全に終わったことを確かめてから、新しいセッションを参加させたい。その手順を文書で知りたい。

**切断中・退出の扱い（今の動きのまま）**
24. 送信者として、切断中の相手にも送りたい。相手が戻ったとき（または同じ ID で別のセッションが入ったとき）に届けばよいから。
25. 送信者として、退出した相手や存在しない ID に送ろうとしたら、エラーで知りたい。届かない相手に送ったつもりにならないように。
26. ユーザーとして、明示的に退出させた担当宛ての未取得メッセージは、配送を止めてほしい。退出は「完全に抜ける」意味だから。
27. ユーザーとして、退出した ID でも、あとで同じ ID で参加し直せるようにしたい。担当の ID を使い回したいから。
28. ユーザーとして、退出のときに配送を止めたメッセージが、参加し直したあとに急に届かないでほしい。古い依頼を誤って実行させないように。
29. 見守る人として、WebUI の参加者の欄で、その ID に今どのハーネスが入っているかを見たい。

**異常時**
30. ユーザーとして、ブローカーだけが再起動したときは、何もしなくてもつながり直してほしい。
31. ユーザーとして、停電などで PC ごと落ちたときの再開の手順を、1か所で読みたい。
32. ユーザーとして、ブローカーが止まっている間に送れなかったメッセージの扱い（同じ `client_message_id` で送り直す）を知りたい。
33. ユーザーとして、前のセッションが「接続中」のまま残ったときの見分け方と対処を知りたい。

## 4. 実装の決定事項

### 4.1 参加の判定（ブローカーの業務処理：会話の中からの参加）

- **ID の指定を必須にする**：ID を省略して会話の中から参加しようとしたら、`INVALID_ARGUMENT` で断る。
  - 案内（hint）：「ID は自分で決めず、どの ID で参加するかユーザーに尋ねてから、もう一度 channel_join してください。」
  - これまでの「`<ハーネス>-<番号>` を自動で付ける」処理はなくす。
- **ハーネスが違うことによる断りをなくす**：登録済みの ID に別のハーネスで参加したら、その ID の次の項目を、参加したセッションのものに書き換える。
  - ハーネス
  - 知らせ方（Codex は `codex queue`、Claude は Channel）
  - 会話 ID：**その参加で指定されたものだけを使う。** 前の値は使わない（Claude は会話 ID を使わないので空にする）。
    - 前の値を残すと、Codex → Claude → Codex の入れ替えや、Codex の新しい会話での参加し直しで、通知が前の会話に送られてしまうため（今のコードは前の値を残している）。
- **Codex が会話 ID なしで参加しようとしたら断る**：`INVALID_ARGUMENT` で断り、何も登録しない。
  - 案内：「シェルで echo $CODEX_THREAD_ID（PowerShell は $env:CODEX_THREAD_ID）を実行し、その値を conversation_id に入れて、もう一度 channel_join してください。」
  - 断られたときは参加していない状態のままなので、会話 ID を付けて呼び直せば参加できる。
  - これにより、会話の中から参加した Codex が「自動受信は未準備」になることはなくなる（今の「会話 ID が未登録」の状態と案内は、会話の中からの参加では使わなくなる）。
- **使用中の判定は、今のまま**：その ID が接続中なら、ハーネスが同じでも違っても断る。
  - 接続中とは、最後の応答から 30 秒以内（`offline_after_ms`）のことです。
  - **参加した時点から使用中として扱う。** 今のコードは、参加のあとブリッジが接続した時点から使用中になる。参加の処理の中で使用中の記録も付け、その間に同じ ID で参加されても確実に断るようにする（仕様の追加ではなく、「使用中なら断る」を正しく実装するための注意）。
- **参加の処理は、1つのトランザクションで行う**：ID・会話 ID・表示名・役割の検査と登録、前のキーの失効、新しいキーの発行、使用中の記録を、まとめて確定する。
  - 表示名の重複（`NAME_TAKEN`）などで断るときは、何も変わらない（キーも使用中の記録も残らない）。
  - 今のコードは、キーの発行を確定してから表示名を登録している。このままだと、表示名で断られたあとに別の表示名で参加し直すと、自分の失敗した参加のせいで 30 秒間 `AGENT_IN_USE` になる。
  - 実装の注意：DB のトランザクション（`db.tx`）は入れ子にできない（中で `BEGIN` をもう一度実行すると失敗する）。表示名と役割を登録する処理は今それ自身のトランザクションを持っているので、トランザクションを持たない部分に切り出して、参加の処理の1つのトランザクションの中から呼ぶ。
- **使用中のときの案内を変える**：`AGENT_IN_USE` の hint を、「別の ID を指定してください」から次の文に変える。
  > 前のセッションがまだ接続中です。別の ID は使わず、ユーザーに伝えて、前のセッションが終了したか確認してもらってください。
- **今のままでよい点**（変更しない）
  - **前のセッションのキーを無効にする**：参加するたびに、その ID のそれまでのトークンを無効にする。入れ替え前のセッションが戻っても認証で断られ、同じ担当が2人にならない。
  - **自動受信の確認をやり直す**：参加するたびに、自動受信の状態を「未確認」に戻す。参加の 8 秒後に確認の通知を送る。
  - **統括の役目は ID に付いたまま**：入れ替えても引き継ぐ。
  - **未取得のメッセージは ID に付いたまま**：新しいセッションの `channel_receive` で受け取れる。
- **退出は、今のまま**
  - 退出すると、未取得は「退出で配送停止」になる。データは消さず、WebUI に × で記録が残る。
  - 退出した ID には送れない（`RECIPIENT_NOT_JOINED`）。
  - 同じ ID で参加し直せる。配送を止めたものは戻さない。

### 4.2 MCP のツール（`channel_join`）

- **`agent_id` を必須の引数にする**：会話の中から参加する方法で起動したブリッジ（トークンファイルなし）では、ツールの定義で必須にし、ブローカー側でも断る。
  - 説明文は「役割の ID（例：dev、planning）。ユーザーに指定されたものを使う。分からなければユーザーに尋ねる」とする。
- **参加済みのときの `agent_id`**
  - 今のブリッジは、トークンファイルで起動した場合と参加済みの場合、`channel_join` を「表示名と役割の更新」として扱い、`agent_id` を見ない。
  - このとき、指定された `agent_id` が今の ID と違えば断る。案内は「このセッションは dev として参加済みです。ID を変えるには、セッションを起動し直してください。」とする。同じ ID なら、今までどおり更新する。
  - トークンファイルで起動したブリッジでは ID が決まっているので、ツールの定義では必須にしない。ブリッジは起動したときにどちらの方法かが分かるので、定義を分けられる。
- **ほかの4つのツールは変えない**

### 4.3 トークンファイルで参加させる方法（管理用 CLI の `provision`）

- 今も `--agent` は必須で、ハーネスを変えて登録し直すこともできる。**変更しない。**

### 4.4 WebUI

- 参加者の欄の「Codex / Claude」の表示は、今のハーネスを出しているので**変更しない。**
- メッセージごとの「送ったときのハーネス」は記録しない（ユーザーの判断：シンプルにする）。

### 4.5 AI に渡す文面

- 運用指示に、「ID はユーザーに指定されたものを使う。分からなければユーザーに尋ねる」を加える（短く）。
- 通知文は変えない。

### 4.6 DB とデータの移行

- **スキーマは変えない**：ハーネスの列は、今も書き換えられる作りです。
- **今の ID の書き換えや禁止はしない**：`codex-main` などの ID は、そのまま使える。

### 4.7 ドキュメント

- **ID の付け方**：MCP_TOOLS の `channel_join`・OPERATIONS の「参加する」・README に、次の3点を書く。
  - 「ID は担当で付け、ハーネスでは付けない」
  - 例の ID（`main`・`dev`・`review`・`planning`）。今の例 `codex-main`・`claude-1` もこれに直す
  - 担当の入れ替えの手順：前のセッションを閉じる → 新しいセッションに「ID は dev で参加して」と頼む → 引き継ぎはセッションどうしで行う
  - Codex の注意：Codex（0.166）は、MCP サーバーを裏で動くプログラム（app-server）の中で会話ごとに動かす。そのため、Codex を閉じても、`/new` で新しい会話にしても、前の会話の MCP サーバーが**1〜2分ほど残り、その間は前の会話が「接続中」**になる（実物で確認）。この間に同じ ID で参加すると `AGENT_IN_USE` で断られるので、1〜2分待ってから参加する。`codex app-server daemon stop` でもすぐに切れるが、動いているすべての Codex のセッションが止まるので、ほかに Codex のセッションがあるときは使わない
- **異常検知と異常処理**：OPERATIONS に1つの節を作り、次の表をまとめる。今の「うまくいかないとき」の表とは、相互に参照させる。

  | 異常 | 気づき方 | 対処 |
  |---|---|---|
  | 前のセッションが「接続中」のまま残った | 参加すると `AGENT_IN_USE`。WebUI でその ID が接続中のまま、応答が返ってこない | 前のセッションを終了させる（ウィンドウを閉じる・プロセスを止める）。AI が固まっていてもプロセスが生きていれば接続中のままなので、終了させることが必要。Claude は閉じればすぐ切断になる。Codex は閉じても（`/new` でも）前の会話の MCP サーバーが1〜2分残るので、1〜2分待ってから参加する |
  | ブローカーだけが再起動した | WebUI が一時的に開けない | 何もしなくてよい。各セッションは 5 秒ごとに再接続を試み、未取得があれば通知し直す |
  | 停電などで PC ごと落ちた | すべて止まる | ブローカーを起動 → AI のセッションを再開（Codex は `codex resume --last`、Claude は `claude --continue` に Channel の引数）→ **同じ ID で**参加し直す |
  | 止まっている間の送信がエラーになった | `BROKER_UNAVAILABLE` | ブローカーの復旧後に、同じ `client_message_id` で送り直す（二重に投稿されない） |

- **記録**
  - DECISIONS に D-017 を追加する：「ID は役割で付ける。ハーネスの違いでは断らない。ID の指定は必須」と、その理由。
  - REQUIREMENTS：「仕様書から変えた点」の2を書き足す。仕様書 §6.2 は「固定の agent_id と元会話 ID は、認証済みの接続情報から決まる」としているが、会話の中から参加する方法では、ID はユーザーが指定し、AI が `channel_join` で渡す。また、同じ ID にどのハーネスでも入れる。参加の試験の根拠に、今回の試験も加える。
  - CHANGELOG：「未リリース」に追記する。
  - ROADMAP：片付いた項目があれば更新する。

## 5. 試験の決定事項

- **良い試験**：外から見える動き（ツールの結果、エラーの code と案内、受け取れるメッセージ）だけを確かめる。DB の列の値など、内部の作りには依存しない。
- **試験する境目**：**MCP ブリッジを MCP クライアントから呼ぶ**。今の「会話の中から参加」の試験と同じ境目を使い、新しい境目は作らない。
  - ブリッジ → 参加用キー → ブローカーまで、通して確かめられる。
- **既存の試験との関係**
  - 今の「会話の中から参加」の試験で ID を省略して Claude を参加させている部分は、「省略すると断られる」の確認に置き換える。
  - Claude の参加には ID を指定する。

**追加・変更する試験**
1. **ID を省略すると断られる**：`channel_join` を `agent_id` なしで呼ぶと断られ、案内に「ユーザーに尋ねる」旨がある。
   - ツールの定義でも `agent_id` が必須になっている（ツール一覧の `inputSchema.required`）。
2. **Codex から Claude への入れ替え**
   1. Codex のブリッジで `dev` として参加し、閉じる（切断中にする）。
   2. 別の参加者から `dev` 宛てに送る（切断中でも送れる）。
   3. Claude のブリッジで `dev` として参加すると成功し、そのメッセージを `channel_receive` で受け取れる。
   4. 参加者の一覧で、`dev` のハーネスが Claude になっている。
   5. Claude 側に自動受信の確認（Channel）が届く。
3. **Claude から Codex への入れ替え**：同じ手順で逆の向きを確かめる。Codex 側には、新しい会話 ID 宛てに `codex queue` が届く。
4. **使用中の ID**：接続中の `dev` に別のセッションが参加しようとすると、`AGENT_IN_USE` になり、案内に「別の ID は使わず、ユーザーに確認」の旨がある。
   - 今の「同じ固定 ID は、接続中なら別のセッションから使えない」の確認を、この案内まで見るように広げる。
5. **前のセッションのキーが無効になる**：入れ替えたあとに前のセッション（のトークン）で呼ぶと、認証で断られる。
   - 前のセッションには、トークンファイルで参加させた参加者（`provision`）を使い、切断中にしてから、会話の中からの参加で同じ ID に入れ替える。そのあと、前のトークンで AI 用の API を呼ぶと 401 になることを確かめる（今の試験と同じ HTTP の呼び方）。
   - ブリッジどうしでは確かめられない。前のブリッジを生かしておくと、ハートビートで接続中のままになり、入れ替えられないため。
6. **会話 ID**
   - Codex で `conversation_id` なしの `channel_join` は断られ、案内に `$CODEX_THREAD_ID` がある。そのあと会話 ID を付けて呼び直すと参加できる。
   - Codex（会話 T1）→ Claude → Codex（会話 T2）の順に入れ替えると、通知（`codex queue`）は T2 にだけ送られ、T1 には送られない。
7. **参加済みのセッションで別の ID**：`dev` として参加したセッションで `agent_id: "review"` を指定して `channel_join` すると断られる。同じ `dev` なら、表示名と役割が更新される。
8. **表示名で断られても ID は使用中にならない**：ほかの参加者と同じ表示名で `dev` に参加して `NAME_TAKEN` で断られたあと、別の表示名ですぐ `dev` に参加すると成功する。
9. **ドキュメントの試験（今の試験11）**：今はトークンファイル付きのブリッジだけで確かめているので、トークンファイルなし（会話の中から参加する方法）のブリッジでも確かめるように直す。これで、必須になった `agent_id` と、Codex の `conversation_id` の説明が MCP_TOOLS にあることを確かめられる。

**実物の CLI での確認**（自動試験とは別に行い、プルリクエストに結果を書く）
- 実物の Codex に「ID は dev で参加して」と頼み、そのあとセッションを閉じて、`dev` が切断中になるのを待つ（1〜2分）。
- 試験係から `dev` 宛てに質問を送る。
- 実物の Claude Code に「ID は dev で参加して」と頼み、質問を受け取って `reply_to` 付きで返信することを確かめる。
- ID を言わずに「キャッチボールに参加して」と頼んだとき、AI がユーザーに ID を尋ねることも確かめる。

## 6. 対象外

- 固まったセッションを強制的に切断する仕組み（管理用 CLI を含む）。人が前のセッションの終了を確かめる運用にする。
- 入れ替わりの自動の知らせ（参加者全員への通知など）。
- メッセージごとの「送ったときのハーネス」の記録と表示。
- 会話の記憶や、受け取り済みのメッセージの引き継ぎ。引き継ぎメモなどで、セッションどうしで行う。
- 既存の ID の書き換えや、ハーネス名の ID の禁止。
- 退出で配送を止めたメッセージを、参加し直したときに戻すこと。
- 退出で配送を止めたメッセージのデータを、物理的に消すこと（WebUI に記録として残す）。

## 7. 補足

- **変更はほとんどブローカーの参加の処理とブリッジの `channel_join` に閉じる**
  - ブローカー：ハーネスで断る判定の削除、ID の必須化、使用中の案内の変更、会話 ID の扱い、参加した時点からの使用中の記録
  - ブリッジ：方法に応じた `agent_id` の扱い
  - ほかは、文面・ドキュメント・試験の変更です。
- **新しい危険はない**：同じハーネスなら、今も切断中の ID で参加し直せる。今回はその条件をハーネスに関係なく同じにするだけなので、乗っ取りの危険が新しく増えるわけではない。接続中の ID は、今までどおり使えない。
- **参加用キーについて**：参加用キー（join.key）を読めるのは、この PC の同じ OS ユーザーだけです。この前提は変わらない（D-012）。
