# 決定事項：ルーム

ユーザーとの質疑（2026-11-02）で決まった内容です。この文書が前提で、[仕様書（rooms.md）](rooms.md) はこれを実装に落としたものです。**ここに書いた決定は、ユーザーの指示なしに変えない。**

## やりたいこと

- 今は1つしかない「チャンネル」を、**ルーム**として複数持てるようにする。
- まずは、ルームの作成・削除・一覧ができるようにする。
- ルームを指定して操作すること以外は、今と同じにする。
- DB は新しく作る。今のデータは捨てる。

## 決まったこと

| # | 項目 | 決定 | 仕様書 |
|---|---|---|---|
| 1 | 同時に入れるルーム | 1つのセッションは、同時に1つのルームにだけ入る。参加（`channel_join`）のときにルームを指定し、そのあとの操作は参加したルームで行う | §4.3・§4.5 |
| 2 | 参加者の ID | ルームごとに別のものとして扱う。ルーム A の `dev` とルーム B の `dev` は別の参加者。決定17の規則（空いていれば入れる、使用中なら断る）は、ルームの中で同じように働く | §4.1・§4.3 |
| 3 | 作成・削除・一覧を使える場所 | MCP ツールだけ（`channel_room_create`・`channel_room_delete`・`channel_rooms`）。CLI と WebUI には作成・削除を足さない | §4.5 |
| 4 | ルームがないとき | 参加しようとしたルームがない、またはルームの指定がないときは断る。「ルームを自分で作らず、どのルームに入るかユーザーに尋ねる」と案内する。AI がルームを作るのは、ユーザーに頼まれたときだけ | §4.3・§4.9 |
| 5 | 削除できる条件 | 全員が退出したら削除できる。くわしくは 9 | §4.2 |
| 6 | ルームの名前 | ルームは ID だけで識別する。表示名は付けない。ID はユーザーが自由に付けられる（文字の決まりは 10） | §4.2 |
| 7 | 今のデータ | 新しい DB は別のファイル名で作る。今の DB ファイルは読まずに、そのまま置いておく。設定の `channel_id` はなくす | §4.1 |
| 8 | WebUI | ルームの一覧から選んで、そのルームの参加者とメッセージを見るだけ。作成・削除はしない | §4.7 |
| 9 | 「全員が退出」の数え方 | 切断したまま退出していない参加者がいるルームは削除できない（消したいときは、その ID で参加し直してから退出させる）。参加者が1人もいないルームは削除できる。登録だけで一度も参加していない ID（`provision`）は、退出済みと同じに数える | §4.2 |
| 10 | ルーム ID の文字 | 英字（大文字・小文字）・数字・ハイフン・ドット・アンダースコアだけ。空白は使えない。長さは 1〜32 文字。大文字と小文字は区別する。同じ ID のルームは作れない | §4.2 |
| 11 | ルームの移り方 | `channel_leave` で退出してから、別のルームで `channel_join` する。再起動は要らない。参加中のまま別のルームを指定したら断り、「先に channel_leave してください」と案内する。トークンファイルで起動したセッションは、ID とルームがファイルで決まっているので移れない | §4.3・§4.5 |
| 12 | CLI の `provision` | ルームの指定を必須にする。ないルームを指定したら断る | §4.8 |
| 13 | 一覧の中身 | ルームの ID、作成した日付、退出していない参加者の「ID と表示名」（例：`dev（開発）`）。切断中の参加者も載せる | §4.2・§4.5 |

**11 の補足**：最初は「移るにはセッションを起動し直す」と提案しましたが、技術的な理由はなかったので取り下げました。退出すれば、ブリッジは参加していない状態に戻り、別のルームに新しく参加できます。通知の届け先（Codex の会話 ID、Claude のチャンネル）はセッションごとのもので、ルームには関係しません。

## 質問せずに決まったこと（ルームに置き換えるだけで決まるもの）

- 統括役は、ルームごとに置く。
- 全員宛て（`all`）の送信は、そのルームの参加者にだけ届く。
- ルームをまたいだ送信はしない。宛先は、自分のルームの中の ID だけ。
- ブリッジは、参加したルームも覚えておく。
- そのほか（受信すれば既読、通知、ハートビート、表示名の重複の判定など）は今と同じで、ルームの中で働く。

## 決定を正しく動かすための実装上の注意

決定は変えません。コードと噛み合わせるための注意です。

- **管理用・閲覧用のトークンを発行し直す**
  - `admin.token` と `viewer.token` は、DB の中の記録とひも付いている。新しい DB では使えない。
  - そのため、新しい DB を作ったときは、この2つを発行し直す。WebUI には、新しい閲覧用トークンでログインし直す（§4.1）。
- **トークンファイルの置き場所**
  - 今は `tokens/<ID>.json` に置いている。ID がルームごとに重なるので、このままでは別のルームの `dev` と同じファイルになる。
  - そのため、ルームごとのフォルダー（`tokens/<ルーム>/<ID>.json`）に分ける（§4.8）。
- **メモリで持つ接続状態**：接続状態などをメモリで持つときの鍵は、今は ID だけ。これを「ルームと ID の組み」にする（§4.1）。
- **退出したあとのブリッジ**：今のブリッジは、退出しても参加したときのキーを持ち続ける。決定11のため、会話の中から参加したブリッジは、退出したらキーを捨てて、参加していない状態に戻る（§4.5）。
- **管理用 CLI の `probe`・`status`・`export`**：ID だけでは参加者が決まらないので、ルームを指定するか、ルームの列を出す（§4.8）。
