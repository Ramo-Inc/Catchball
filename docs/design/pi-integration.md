# 仕様：Pi（pi-coding-agent）の参加と自動受信

> **この文書は実装前に書いた仕様書です。** 文中の「今の作り」は、この文書を書いた時点（2026-11-02、`main`）の状態を指します。作り方の詳しいことと、調査・試作の結果は [pi-integration-design.md](pi-integration-design.md)（設計書）にあります。

- 状態：**未実装**（調査と試作まで済み）
- 対象の Pi：`@earendil-works/pi-coding-agent` 1.5.0（リポジトリは `earendil-works/pi`。旧名 pi-mono）
- 方針：**要件を満たす最小の変更にする。** 変えるのは、ブリッジと、新しく足す Pi 用の拡張機能だけ。ブローカー・DB・WebUI・管理用 CLI は変えない

## 1. 困っていること

- **Pi は参加できるが、自分からは動かない**
  - Pi は MCP を内蔵しているので、session_mail を登録すれば8つのツールを使えます。実物で、ルームの作成から削除まで通りました。
  - しかし、新着が届いても Pi は動きません。ユーザーが「受信して」と頼むまで、未取得のまま残ります。
  - 原因：Pi の MCP は、ログとツール一覧の変更以外の通知を捨てます。Claude 用の通知（`claude/channel`）は届きません。
- **そのままでは Codex と見なされる**
  - Pi は MCP の接続で `pi` と名乗ります。今のブリッジは「Claude 以外は Codex」と判定するので、参加のときに Codex の会話 ID を求めます。
- **退出とルームの削除で確認が出ない**
  - Pi はツールを呼ぶたびの承認を求めません。Codex と Claude では、この2つだけ確認させる設定を勧めています。

## 2. 解決のしかた

- **Pi 用の拡張機能を、Catchball に同梱する。** ユーザーは Pi にこれを1回だけ入れます。session_mail の登録も拡張機能が行うので、mcp.json は書きません。
- **通知は、拡張機能を通して Pi の会話に入れる。**
  - ブリッジは、通知（本文なし）を、拡張機能がこの PC の中だけに開いた受け口へ渡します。
  - 拡張機能は、Pi の公式の機能（`pi.sendMessage`）で、通知を会話に入れます。
  - Pi が待機中ならすぐ動き出し、作業中なら作業が終わってから処理します。
  - Pi は、ほかの AI と同じく、`channel_receive` で本文を取りに行きます。
- **ブローカーの中では、Pi を「Claude と同じ種類」として扱う。**
  - Claude と同じく、通知はハートビートで手渡しします。会話 ID は求めません。再通知や送り直しの決まりも同じです。
  - そのため、ブローカーは変えずに済みます。
- **退出とルームの削除の前に、拡張機能が Pi の画面で確認を出す。**

## 3. ユーザーストーリー

**導入**
1. ユーザーとして、Pi に Catchball の拡張機能を1つ入れるだけで使えるようにしたい。mcp.json を手で書かずに済むからです。
2. ユーザーとして、拡張機能を Pi の普通の方法（`pi install <フォルダー>`）で入れたい。Pi の使い方から外れないからです。
3. ユーザーとして、拡張機能には、同じ Catchball のフォルダーのブリッジを使ってほしい。パスを設定しなくて済むからです。
4. ユーザーとして、ブリッジがまだビルドされていないときは、Pi の画面に「npm run build をしてください」と出てほしい。何が足りないかがすぐ分かるからです。
5. ユーザーとして、`SESSION_MAIL_HOME` の設定が、Pi から起動したブリッジにも効いてほしい。ほかの AI と同じブローカーにつながるからです。

**参加と送受信**
6. Pi のセッションとして、Codex・Claude と同じ `channel_join`（ルーム・ID・表示名・役割）で参加したい。同じ手順で使えるからです。
7. Pi のセッションとして、Codex の会話 ID を求められたくない。Pi には、その ID がないからです。
8. Pi のセッションとして、送信・返信・受信・参加者の一覧・ルームの操作を、ほかの AI と同じツールで使いたい。決まりが1つで済むからです。
9. ユーザーとして、統括・担当のどちらでも、役割の ID の引き継ぎ（D-017）でも、ルームの移動でも、Pi をほかの AI と同じように使いたい。

**自動受信**
10. ユーザーとして、Pi が待機中に新着が届いたら、Pi が自分から受信して対応してほしい。いちいち頼まずに済むからです。
11. ユーザーとして、Pi が作業中に新着が届いたら、作業が終わってから受信してほしい。作業が途中で乱れないからです。
12. ユーザーとして、Pi の画面で、Catchball の通知が届いたことが見えてほしい。Pi がなぜ動き出したかが分かるからです。
13. ユーザーとして、通知に本文を入れないでほしい（今と同じ）。本文は `channel_receive` で取り、既読が記録されるからです。
14. ユーザーとして、参加の直後に自動受信の確認が走り、本当に届いたときだけ WebUI に「自動受信 確認済み」と出てほしい。誤った表示で安心しないためです。
15. ユーザーとして、通知を会話に入れられなかったときは、WebUI に失敗として出て、間隔を空けて送り直してほしい（今の D-019 と同じ）。黙って止まらないためです。
16. ユーザーとして、未取得が長く残ったら、今の Claude と同じく、時間を空けて通知し直してほしい。中断などで通知が流れても、取りこぼさないためです。

**確認と安全**
17. ユーザーとして、Pi が退出する前とルームを削除する前に、Pi の画面で確認を求められたい。うっかり抜けたり消したりしないためです。
18. ユーザーとして、確認で断ったら、Pi に「ユーザーが断った」と伝わってほしい。Pi が勝手にやり直さないためです。
19. ユーザーとして、受け口には、この PC で同じユーザーが動かしているブリッジしかつなげないようにしたい。偽の通知を入れられないためです。
20. ユーザーとして、今の安全性の決まり（AI 用の API は 127.0.0.1 だけ、送信元はトークンで決める、通知に本文を入れない、承認を中継しない、ログにトークンや本文を書かない）を、Pi でも守ってほしい。

## 4. 実装の決定事項

**変える部品は2つだけ**
- **Pi 用の拡張機能（新しく作る）**
  - Catchball のリポジトリに同梱する。Pi のパッケージの形（`package.json` の `pi.extensions`）にする。
  - ビルドしない JavaScript（ESM）で書き、Catchball の `tsc` の対象には入れない。
- **ブリッジ（今のものを少し変える）**
  - ブローカー・DB・WebUI・管理用 CLI・AI に渡す文面は変えない。

**拡張機能の役目（4つ）**
1. Pi のセッションの開始時に、受け口を開く（この PC の中だけのもの）。
2. ブリッジを `session_mail` として登録する（`pi.registerMcpServer`）。
   - ツールがモデルに直接見えるよう、見せ方は `direct` にする。
   - 受け口の場所と合言葉を、環境変数でブリッジに渡す。
3. 受け口に届いた通知を、`pi.sendMessage` で会話に入れる。設定は `triggerTurn: true`・`deliverAs: "followUp"`・画面に表示。入れられたら `written`、例外なら `error` を返す。
4. `channel_leave` と `channel_room_delete` の前に確認を出す（`tool_call` のイベントで止め、`ctx.ui.confirm` で聞く）。断られたら、実行せずに理由を返す。

**ブリッジの変更**
- **種類の判定**：接続名が `pi` のとき（または `SESSION_MAIL_PROVIDER=pi` のとき）は、ブローカーに「Claude」として参加する。
- **通知の届け先**：受け口の場所が環境変数にあるときは、通知を `claude/channel` ではなく受け口に送り、返事（`written` か `error`）を次のハートビートで返す。
- **失敗の扱い**：受け口につながらない、返事が来ない（数秒で時間切れ）ときは、`error` として返す。ブローカーは今の決まりどおり、失敗を記録して送り直す。
- **拡張機能なしの Pi**（mcp.json だけで登録した Pi）では、受け口がないので通知は `error` になる。WebUI には、通知の失敗として「Pi の拡張機能がありません」と出る。

**受け口とやり取りの形**
- Node の `net` で開く。Linux・Mac は、OS の一時フォルダーの下に作った本人だけのフォルダーの Unix ソケット。Windows は名前付きパイプ。
- 合言葉は、セッションの開始のたびに乱数で作り、環境変数でブリッジにだけ渡す。ブリッジは最初の1行で合言葉を送り、合わなければ拡張機能が切る。
- 1行に1つの JSON で、次の4つだけ送る。

```jsonc
// ブリッジ → 拡張機能
{"type":"hello","secret":"<合言葉>"}
{"type":"notify","notify_id":"n_…","content":"<通知文（本文なし）>"}
// 拡張機能 → ブリッジ
{"type":"result","notify_id":"n_…","result":"written"}
{"type":"result","notify_id":"n_…","result":"error","error":"<理由>"}
```

**ブローカーの側で、そのまま効くこと**（Claude と同じ種類として扱うため）
- 参加のときに会話 ID を求めない。
- 参加のあとに確認用の通知を出し、通知のあとに受信があれば「確認済み」にする。返事は受け口から `written` が返ったときだけ出すので、前の試験で出た誤表示は起きない。
- 未取得が残れば、5分・15分・30分で通知し直す。通知に失敗したら、30秒・2分・10分で送り直す。
- 再接続のときに、未取得があれば通知する。

**分かっていて受け入れること**
- WebUI と `status` では、Pi の種類が「Claude」と表示される。「Pi」と出すには DB の変更が要るので、今回は入れない。

## 5. 試験の決定事項

**良い試験とは**：外から見える動きだけを確かめる。受け口に何が届くか、ブローカーの状態（WebUI の API・`status` に出るもの）がどう変わるか、拡張機能が Pi の API をどう呼ぶか。内部の関数や DB の列を直接見ない。

**試験の境目（2つ）**
1. **ブリッジ**
   - 今の自動試験の「MCP ブリッジ」「会話の中から参加」と同じく、試験がブリッジを子プロセスで起動し、接続名 `pi` の MCP クライアントで話す。
   - 試験自身が、拡張機能の代わりに受け口を開き、場所と合言葉を環境変数で渡す。
   - 確かめること：
     - 会話 ID なしで参加できる。
     - 確認用の通知が受け口に届き、`written` を返して受信すると「確認済み」になる。
     - 新着の通知に本文が入っていない。
     - `claude/channel` の通知が出ない。
     - `error` を返すと失敗が記録される。
     - 合言葉が違うと届かない。
     - 受け口がないと、通知が失敗になる。
2. **拡張機能**
   - 拡張機能の入口の関数に、Pi の API の偽物（`on`・`registerMcpServer`・`sendMessage`・`ui.confirm` の呼ばれ方を記録するだけのもの）を渡して読み込む。
   - 確かめること：
     - セッションの開始で受け口が開き、`session_mail` が `direct` で登録される。
     - 届いた通知が、決めた設定で `sendMessage` に渡る。
     - 退出・削除の前に確認が出て、断ると止まる。
     - セッションの終了で受け口が閉じる。

**前例**：自動試験の「MCP ブリッジ：8ツール、Claude には channel 通知、Codex には codex queue」「会話の中から参加」。

**実物での試験**
- 実物の Pi 1.5.0（モデルは Haiku。料金を抑えるため）で確かめ、`docs/verification/` に記録する。
- 確かめること：
  - 拡張機能を入れて参加すると、「確認済み」になる。
  - 相手から送ると、Pi が自分から受信して返信する。
  - 作業中に届いたものは、作業のあとに処理される。
  - Esc で中断したあとも、再通知で受信される。
  - 退出と削除で確認が出る。

## 6. 対象外

- WebUI・`status` で「Pi」と表示すること（DB の変更が要るため）。
- Pi を `-p`（1回答えて終わる）や JSON モードで動かしたときの自動受信。プロセスが終わるので、届ける先がない。
- 拡張機能が自分でツールを持つ形、Pi を外から RPC で操る形、拡張機能がブローカーを問い合わせる形（比べた結果は設計書の §3）。
- 承認待ちの検知（R-4）。Pi は承認を求めないので、対象がない。
- 拡張機能を npm や pi.dev で公開すること。

## 7. 決めること（実装の前にユーザーに確かめる）

1. **確認画面を出せないとき**（`-p` など、Pi の画面がないとき）の、退出と削除の扱い
   - 案A（推奨）：確認なしで実行する。`-p` は、人が書いた手順で動かすため。
   - 案B：実行せず、「ユーザーに確かめてください」と返す。
