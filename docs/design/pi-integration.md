# 仕様：Pi（pi-coding-agent）の参加と自動受信

> **この文書は実装前に書いた仕様書です。** 文中の「今の作り」「今は〜」は、この文書を書いた時点（2026-11-02、`main` の ca4d1c2）の状態を指します。作りの詳しいことは [pi-integration-design.md](pi-integration-design.md)（設計書）に書きます。

- 状態：**未実装**（調査と試作まで済み。§7 の「決めること」をユーザーに確かめてから実装する）
- 対象：v1.0.0-alpha.1 の次（ルームが入った今の `main`）
- 対象の Pi：`@earendil-works/pi-coding-agent` 1.5.0（ソースは `earendil-works/pi`。旧名 pi-mono）
- 根拠：Pi の公式ドキュメント（extensions.md・mcp.md・rpc.md・security.md）、Pi のソース、実物の Pi（Haiku）での試験と試作。詳しくは設計書の §2

## 1. 困っていること

- **Pi は Catchball に参加できるが、自分からは動かない**
  - Pi は MCP を内蔵しているので、session_mail のブリッジを登録すれば、8つのツールは使えます。実物で、ルームの作成・参加・受信・返信・退出・削除まで通りました。
  - しかし、新着が届いても Pi は動きません。ユーザーが「受信して」と頼むまで、メッセージは未取得のまま残ります。
  - 原因：Pi の MCP は、ログとツール一覧の変更以外の通知を捨てます。Claude 用の通知（`claude/channel`）を送っても、Pi は受け取りません。拡張機能に MCP の通知を渡す口もありません。
- **Pi は「Codex」と見なされる**
  - Pi は MCP の接続で `pi` と名乗ります。今のブリッジは「Claude 以外は Codex」と判定します。
  - そのため、参加のときに Codex の会話 ID を求められます。ブローカーは `codex queue` で通知しようとして、失敗します。
- **回避策では、表示が誤る**
  - 環境変数 `SESSION_MAIL_PROVIDER=claude` で Claude 扱いにすれば、参加はできます。
  - しかし、WebUI の種類は「Claude」と出ます。ユーザーが手で受信させると、「自動受信 確認済み」とまで出ます。実際には自動受信できていません。
- **退出とルームの削除で確認が出ない**
  - Pi は、ツールを呼ぶたびの承認を求めません。
  - Codex と Claude では、退出と削除の前に確認させていますが、Pi では確認なしで実行されます。

## 2. 解決のしかた

- **Pi 用の拡張機能を、Catchball に同梱する**
  - ユーザーは、Pi にこの拡張機能を1回だけ入れます。session_mail の登録（mcp.json）は、拡張機能が代わりに行います。
- **通知は、拡張機能を通して Pi の会話に入れる**
  - ブリッジは、通知（本文なし。「未取得が N 件あります」だけ）を、拡張機能がこの PC の中だけに開いた受け口へ渡します。
  - 拡張機能は、Pi の公式の機能（`pi.sendMessage`）で、通知を会話に差し込みます。
  - Pi が待機中なら、すぐに動き出します。作業中なら、今の作業が終わってから処理します。作業を途中で邪魔しません。
  - Pi は、Codex や Claude と同じように、`channel_receive` で本文を取りに行きます。
- **ブローカーに「Pi」という種類を足す**
  - WebUI・`status`・参加者の一覧で「Pi」と表示します。
  - 自動受信の確認（参加のときの確認用の通知）も、Codex・Claude と同じしくみで、本当に届いたときだけ「確認済み」にします。
- **退出とルームの削除の前に、拡張機能が確認画面を出す**
- **ツールや、AI に渡す文面は、今のものをそのまま使う**
  - Pi に見える8つのツールと使い方は、Codex・Claude と同じです。MCP_TOOLS.md の1枚で使えます。

## 3. ユーザーストーリー

**導入**
1. ユーザーとして、Pi に Catchball の拡張機能を1つ入れるだけで、Catchball を使えるようにしたい。mcp.json を手で書かずに済むからです。
2. ユーザーとして、Catchball のフォルダーにある拡張機能を、Pi の普通の方法（`pi install <フォルダー>` か、設定の `packages`）で入れたい。Pi の使い方から外れないからです。
3. ユーザーとして、拡張機能が見つけるブリッジは、同じ Catchball のフォルダーのものにしたい。パスを設定しなくて済むからです。
4. ユーザーとして、ブリッジがまだビルドされていないときは、Pi の画面に「npm run build をしてください」と出てほしい。何が足りないかがすぐ分かるからです。
5. ユーザーとして、すでに mcp.json に session_mail を書いているときは、それより拡張機能の登録を優先するか、二重になっていると知らされたい。古い回避策の設定が残っていても混乱しないためです。
6. ユーザーとして、Catchball の普段のデータフォルダー（`SESSION_MAIL_HOME`）の設定が、Pi から起動したブリッジにも効いてほしい。ほかの AI と同じブローカーにつながるからです。

**参加**
7. Pi のセッションとして、Codex・Claude と同じ `channel_join` で、ルーム・ID・表示名・役割を指定して参加したい。同じ手順で使えるからです。
8. Pi のセッションとして、参加のときに Codex の会話 ID を求められたくない。Pi には、その ID がないからです。
9. ユーザーとして、WebUI と `status` で、その参加者が「Pi」だと分かるようにしたい。Codex・Claude と見分けられるからです。
10. ユーザーとして、Pi が統括（coordinator）としても担当（worker）としても参加できるようにしたい。役割の分け方は AI の種類と関係ないからです。
11. ユーザーとして、役割の ID を、Pi と Codex・Claude のあいだで引き継げるようにしたい（D-017）。担当の AI を入れ替えても、ID と未取得のメッセージが残るからです。
12. ユーザーとして、ルームの移動（退出してから参加）を、Pi でも再起動なしでしたい。Codex・Claude と同じ動きだからです。

**自動受信**
13. ユーザーとして、Pi が待機しているときに新着が届いたら、Pi が自分から受信して対応してほしい。いちいち「受信して」と頼まずに済むからです。
14. ユーザーとして、Pi が作業中に新着が届いたら、今の作業が終わってから受信してほしい。作業が途中で乱れないからです。
15. ユーザーとして、Pi の画面に、Catchball からの通知が届いたことが見えるようにしたい。Pi がなぜ動き出したかが分かるからです。
16. ユーザーとして、通知には本文を入れないでほしい（今と同じ）。本文は、Pi が `channel_receive` で取り、既読が記録されるからです。
17. ユーザーとして、未取得が残っているあいだに新着が重なっても、通知が何度も積み上がらないでほしい（今と同じ「1件まで」）。Pi が空の受信を繰り返さないためです。
18. ユーザーとして、参加した直後に自動受信の確認が走り、届けば WebUI に「自動受信 確認済み」と出てほしい。準備ができたことが分かるからです。
19. ユーザーとして、拡張機能が入っていない Pi（mcp.json だけで登録した Pi）では、「自動受信 未設定」と正しく出てほしい。誤って「確認済み」と出ないためです。
20. ユーザーとして、Pi を終了して起動し直したら、未取得があれば、また通知が届いてほしい（今の再接続と同じ）。取りこぼさないためです。
21. ユーザーとして、通知を会話に入れられなかったときは、WebUI の「宛先ごとの状況」に失敗として出て、間隔を空けて送り直してほしい（D-019 と同じ）。黙って止まらないためです。

**送信と受信**
22. Pi のセッションとして、個別・全員宛ての送信、返信（reply_to）、受信、参加者の一覧を、Codex・Claude と同じように使いたい。決まりが1つで済むからです。
23. ユーザーとして、Pi が送ったメッセージの送信元が、必ず Pi の参加者になってほしい（トークンで決める。今と同じ）。ほかの参加者になりすませないためです。

**確認**
24. ユーザーとして、Pi がルームから退出する前に、Pi の画面で確認を求められたい。Codex・Claude と同じく、うっかり抜けないためです。
25. ユーザーとして、Pi がルームを削除する前に、Pi の画面で確認を求められたい。削除は元に戻せないからです。
26. ユーザーとして、確認で「いいえ」を選んだら、Pi に「ユーザーが断った」と伝わってほしい。Pi が勝手にやり直さないためです。
27. ユーザーとして、それ以外のツール（参加・送信・受信・一覧・ルームの作成）は、確認なしで使えるようにしたい。Codex・Claude の推奨設定と同じだからです。

**安全**
28. ユーザーとして、拡張機能の受け口には、この PC のこのユーザーしかつなげないようにしたい。ほかのプロセスが、偽の通知を入れられないためです。
29. ユーザーとして、受け口はネットワークに出ないでほしい。AI 用の API は 127.0.0.1 だけ、という今の決まりを守るためです。
30. ユーザーとして、Pi の会話や拡張機能のログに、トークンやメッセージの本文が出ないでほしい（今の決まりと同じ）。
31. ユーザーとして、承認をメッセージで中継する機能は、Pi でも入れないでほしい（今の決まりと同じ）。

**使い方の範囲**
32. ユーザーとして、Pi のふだんの画面（TUI）で自動受信が働いてほしい。普段はそこで作業するからです。
33. ユーザーとして、Pi の RPC モードでも自動受信が働いてほしい。ほかのアプリから Pi を動かすときにも使えるからです。
34. ユーザーとして、Pi を `-p`（1回だけ答えて終わる）で動かしたときは、自動受信がないことが分かってほしい。終わったプロセスには通知が届かないからです。
35. ユーザーとして、Windows でも同じように使いたい。Catchball は Windows でも使う前提だからです。

**ドキュメント**
36. ユーザーとして、README・OPERATIONS に、Pi の導入と起動の手順が書いてあってほしい。Codex・Claude と同じように始められるからです。
37. Pi のセッションとして、MCP_TOOLS.md の1枚で使い方が分かってほしい（Pi だけの違いは短く書く）。

## 4. 実装の決定事項

**全体の形**
- Pi 用の拡張機能を1つ作り、Catchball のリポジトリに同梱する。Pi のパッケージの形（`package.json` の `pi.extensions`）にして、`pi install <Catchball のフォルダーの中の場所>` で入れられるようにする。
- 拡張機能は **ビルドしない JavaScript（ESM）** で書く。Pi は .js の拡張機能をそのまま読み込める。Catchball の `tsc` の対象にも入れない（Pi の型の package に依存しないため）。
- **8つのツールは今のブリッジがそのまま出す。** 拡張機能は、ツールを持たない。ツールの定義が二重にならない。
- 拡張機能の役目は4つ。
  1. Pi のセッションの開始時に、受け口を開く。
  2. ブリッジを MCP サーバーとして登録する（`pi.registerMcpServer`）。
  3. ブリッジから届いた通知を、会話に差し込む（`pi.sendMessage`）。
  4. 退出と削除のツールの前に、確認を出す（`tool_call` のイベントと `ctx.ui.confirm`）。

**拡張機能がブリッジを登録するときの設定**
- 名前は `session_mail`。ツール名は、今と同じ `mcp__session_mail__channel_*` になる。
- 見せ方（exposure）は `direct`。Pi の既定（codemode）では、ツールがモデルに直接見えないため。
- ブリッジに渡す環境変数：
  - 種類を示すもの（`SESSION_MAIL_PROVIDER=pi`）
  - 受け口の場所
  - 受け口に入るための合言葉（起動のたびに作る乱数）
- `SESSION_MAIL_HOME` は、Pi の環境にあれば、そのまま引き継ぐ。
- mcp.json に同じ名前があると、Pi はそちらを優先する（Pi の仕様）。その場合は、Pi の画面に「mcp.json の session_mail を消してください」と知らせる。

**受け口と、やり取りの形**
- 受け口は、この PC の中だけのもの。
  - Linux と Mac：Unix ソケット。本人だけが読み書きできるフォルダーに置く。
  - Windows：名前付きパイプ。名前に乱数を入れる。
- 1行に1つの JSON を送る。
  - ブリッジ → 拡張機能：最初に合言葉。そのあと通知（`notify_id`・通知文・種類（新着か確認用か）・未取得の件数）。
  - 拡張機能 → ブリッジ：通知ごとの結果（`written` か `error`）。
- 合言葉が合わない接続は、すぐ切る。
- 通知文は、今のブローカーが作る文面（本文なし）をそのまま使う。

**会話への差し込み方**
- `pi.sendMessage` を、`triggerTurn: true`・`deliverAs: "followUp"` で呼ぶ。
  - 待機中なら、すぐ動き出す。
  - 作業中なら、作業がすべて終わってから処理する。
- 画面に表示する（`display: true`）。種類は `catchball`。
- 結果を `written` として返すのは、`pi.sendMessage` が例外なく受け付けたとき。例外なら `error` とその理由を返す。

**ブリッジ**
- 種類の判定を、Codex・Claude・Pi の3つにする。
  - 環境変数で指定されていれば、それに従う。
  - なければ、MCP の接続の名前で判定する（`pi` なら Pi）。
- Pi のときは、`claude/channel` の通知を送らない。代わりに、ハートビートの応答で受け取った通知を、受け口へ渡す。結果は、次のハートビートでブローカーに返す（今の Claude と同じ流れ）。
- 受け口の情報が環境変数にない Pi（mcp.json だけで登録した Pi）は、通知を受け取れない。接続のときに、その旨をブローカーへ伝え、「自動受信 未設定」にする。
- 受け口に一時的につながらないときは、`error` として返す（ブローカーが D-019 の間隔で送り直す）。

**ブローカー**
- 参加者の種類に `pi` を、通知の経路に「Pi の拡張機能」を足す。通知の経路は、今の Claude と同じく「ハートビートで手渡し」にする。
- 時間ごとの再通知（Claude の 5・15・30 分）は、Pi にはしない。
  - Pi の `followUp` は、Pi のプロセスが動いているあいだは保持され、作業が終われば必ず処理される（Codex の queue と同じ考え方）。
  - 通知に失敗したときの送り直し（D-019）と、再接続時の通知は、今と同じく行う。
- 「直前にツールを使っていたら少し待つ」（Codex 用）は、Pi にはしない。この点は §7 で確かめる。
- DB の制約（`provider` と `receiver_kind` の値の一覧）に Pi を足す。今の DB ファイルの扱いは §7 で確かめる。
- 参加（`channel_join`）のとき、Pi には会話 ID を求めない。
- 管理用 CLI の `provision --provider` に `pi` を足す。

**WebUI**
- 種類の表示に「Pi」を足す。番号のアイコンの色も、Pi 用に1つ足す。

**AI に渡す文面**
- 運用指示と通知文は、今のものを使う。ただし、Codex・Claude 向けに書き分けている箇所は、Pi では Claude と同じ扱いにする（会話 ID を求めない）。

**変えないこと**
- 安全性の決まり（AGENTS.md）はすべて守る。受け口は PC の外に出ない。通知に本文を入れない。送信元はトークンで決める。`claude/channel/permission` は宣言しない。

## 5. 試験の決定事項

**良い試験とは**：外から見える動きだけを確かめる。具体的には、ブリッジが受け口に何を送るか、ブローカーの状態（WebUI の API・`status` に出るもの）がどう変わるか。内部の関数や DB の列を直接見ない。

**試験の境目（シーム）**
- **境目1（主）：ブリッジを MCP クライアントから起動する、今の試験の形。**
  - 自動試験（`test/main.test.mjs`）の「MCP ブリッジ」「会話の中から参加」の試験と同じく、試験がブリッジを子プロセスで起動する。
  - 試験自身が、Pi の拡張機能の代わりに受け口を開き、合言葉と受け口の場所を環境変数でブリッジに渡す。
  - MCP の接続名は `pi` にする。
  - ここで確かめること：
    - 参加すると、Pi として登録され、会話 ID を求められないこと
    - 確認用の通知が受け口に届き、`written` を返して受信すると「確認済み」になること
    - 新着の通知に本文が入っていないこと
    - `claude/channel` の通知が送られないこと
    - `error` を返すと、失敗が記録され、間隔を空けて送り直されること
    - 合言葉が違う接続が断られること
    - 受け口の情報がないと「未設定」になること
- **境目2：拡張機能を、偽の Pi の API で読み込む。**
  - 拡張機能の入口の関数に、`on`・`registerMcpServer`・`sendMessage`・`ui.confirm` を記録するだけの偽物を渡す。
  - ここで確かめること：
    - セッションの開始で受け口が開き、`session_mail` が `direct` で登録されること
    - 受け口に届いた通知が、`triggerTurn: true`・`deliverAs: "followUp"` で `sendMessage` に渡ること
    - 退出・削除の前に確認が出て、断ると止まること
    - セッションの終了で受け口が閉じ、ファイルが消えること
- 2つの境目は、受け口のやり取りの形（1行1つの JSON）でつながる。この形は、両方の試験で同じものを使う。

**前例**
- 試験の「MCP ブリッジ：8ツール、Claude には channel 通知、Codex には codex queue」「会話の中から参加」（ブリッジを子プロセスで起動し、偽の MCP クライアントで通知を受ける形）。

**実物での試験（自動試験とは別）**
- 実物の Pi 1.5.0（モデルは Haiku。料金を抑えるため）で確かめる。
  - 拡張機能を入れる。
  - ルームを作って参加し、自動受信の確認が「確認済み」になる。
  - 相手から送ると、Pi が自分から受信して返信する。
  - 作業中に届いたものは、作業のあとに処理される。
  - 退出と削除で確認が出る。
- 相手役は、Catchball の送受信の CLI、または実物の Codex・Claude。
- 記録は `docs/verification/` に残す。

## 6. 対象外

- Pi を `-p`（1回だけ答えて終わる）・JSON モードで動かしたときの自動受信。プロセスが終わるため、届ける先がない。手動の受信だけ使える。
- 拡張機能が自分でツールを持つ形（ブリッジを使わない形）。ツールの二重化を避けるため。
- Pi を外から RPC で操る形の自動受信（Pi のふだんの画面が使えなくなるため）。
- 承認待ちの検知（R-4）。Pi は承認を求めないので、対象がない。
- Pi のパッケージとして npm や pi.dev のカタログに公開すること。
- Pi 以外の AI（OpenCode など）への対応。

## 7. 決めること（実装の前にユーザーに確かめる）

1. **今の DB ファイルの扱い**
   - DB の制約に Pi を足すと、今の `session-mail-v2.db` はそのままでは使えない。
   - 案A（推奨）：起動時に、今の DB の表を作り直して Pi を足す。データは残る。
   - 案B：ルームのときと同じく、新しい DB ファイルにし、前のデータは引き継がない。
2. **確認画面を出せないモード**（RPC 以外で UI がないとき。`-p` など）での、退出と削除の扱い
   - 案A（推奨）：確認なしで実行する。`-p` は、人が書いた手順で動かすため。
   - 案B：実行せず、「ユーザーに確かめてください」と返す。
3. **Pi が作業中に届いた通知を、`followUp`（作業がすべて終わってから）にするか、`steer`（今のツールの実行が終わったら割り込む）にするか**
   - 推奨は `followUp`。Catchball の「作業を邪魔しない」方針どおり。
4. **Esc で中断したあとに、待っていた通知がどうなるか**（Codex の K-2 に当たること）
   - 実物で確かめて、消える場合は、再接続と同じように送り直すかを決める。
5. **「直前にツールを使っていたら少し待つ」（Codex の K-1 対策）を Pi にも入れるか**
   - 推奨は「入れない」。Pi の `followUp` は作業中なら後回しになるので、空のターンは起きにくい。実物で確かめる。

## 8. 補足
