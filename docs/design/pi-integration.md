# 仕様：Pi（pi-coding-agent）の参加と自動受信

> **この文書は実装前に書いた仕様書で、記録として残しています。** 今の動きは [ARCHITECTURE](../ARCHITECTURE.md)・[OPERATIONS](../OPERATIONS.md) で確かめてください。 文中の「今の作り」は、この文書を書いた時点（2026-11-02、`main`）の状態を指します。調査・試作の結果と作り方は [pi-integration-design.md](pi-integration-design.md)（設計書）にあります。

- 状態：**実装済み**（2026-11-02。D-020。実物の Pi で確認：[verification/pi-20261102.md](../verification/pi-20261102.md)）
- 対象の Pi：`@earendil-works/pi-coding-agent` 1.5.0（リポジトリは `earendil-works/pi`。旧名 pi-mono）
- 方針：**Codex・Claude Code とまったく同じ機能・同じ使い方にする。** Codex・Claude にないものは足さない

## 1. 困っていること

- Pi は MCP を内蔵しているので、session_mail を登録すれば8つのツールを使えます。実物で、ルームの作成から削除まで通りました。
- しかし、新着が届いても Pi は自分からは動きません。ユーザーが「受信して」と頼むまで、未取得のまま残ります。
  - 原因：Pi の MCP は、ログとツール一覧の変更以外の通知を捨てます。ブリッジが Claude に送っている通知（`claude/channel`）は、Pi には届きません。
- また、今のブリッジは「Claude 以外は Codex」と判定します。そのため、Pi は参加のときに Codex の会話 ID を求められます。

## 2. 解決のしかた

Codex・Claude と同じ形にそろえます。

| | Codex | Claude Code | Pi（この仕様） |
|---|---|---|---|
| session_mail の登録 | ユーザーが `config.toml` に書く | ユーザーが `claude mcp add` する | ユーザーが `mcp.json` に書く |
| 自動受信のための準備 | なし | 起動時の引数 `--dangerously-load-development-channels` | **Catchball の Pi 拡張機能を入れる** |
| ブリッジの種類の判定 | 接続名から自動 | 接続名から自動 | 接続名から自動（**Claude と同じ扱い**） |
| 通知の届け方 | ブローカーが `codex queue` | ブリッジが `claude/channel` で送る | **ブリッジが拡張機能の受け口に書き、拡張機能が `pi.sendMessage` で会話に入れる** |
| ツール・参加・送受信・確認・再通知・送り直し | 今の作り | 今の作り | Claude と同じ（今の作りのまま） |

- Pi の拡張機能は、Claude の起動時の引数と同じ位置づけです。役目は「通知を受け取って会話に入れる」ことだけです。
- ブローカーから見ると、Pi は Claude と同じ参加者です。ブローカーは変えません。

## 3. ユーザーストーリー

1. ユーザーとして、Codex・Claude と同じく、session_mail を MCP サーバーとして登録して Pi を使いたい。手順がそろっているからです。
2. ユーザーとして、Claude で起動時の引数を付けるのと同じく、Pi に Catchball の拡張機能を入れるだけで、自動受信できるようにしたい。
3. Pi のセッションとして、Codex・Claude と同じ8つのツールで、参加・送信・受信・ルームの操作をしたい。決まりが1つで済むからです。
4. Pi のセッションとして、Claude と同じく、参加のときに会話 ID を求められたくない。Pi には、その ID がないからです。
5. ユーザーとして、Pi が待機中に新着が届いたら、Pi が自分から受信して対応してほしい。Codex・Claude と同じだからです。
6. ユーザーとして、Pi が作業中に新着が届いたら、作業が終わってから受信してほしい。Codex・Claude と同じく、作業が途中で乱れないためです。
7. ユーザーとして、自動受信の確認・再通知・送り直しが、Claude と同じように働いてほしい。
8. ユーザーとして、今の安全性の決まり（AI 用の API は 127.0.0.1 だけ、送信元はトークンで決める、通知に本文を入れない、承認を中継しない、ログにトークンや本文を書かない）を、Pi でも守ってほしい。

## 4. 実装の決定事項

**ブリッジ（2か所だけ変える）**
1. **種類の判定**：接続名が `pi` のときは、Claude と同じ扱いにする（ブローカーには `claude` として参加する）。
2. **通知の届け方**：接続名が `pi` のときは、`claude/channel` で送る代わりに、Pi の拡張機能の受け口に1行書く。書けたら `written`、書けなければ `error` を返す（今の Claude の通知と同じ返し方）。

**Pi の拡張機能（新しく作る）**
- ビルドしない JavaScript の1ファイル。Catchball のリポジトリに同梱する。
- 役目は次の2つだけ。
  1. Pi のセッションの開始時に受け口を開き、終了時に閉じる。同じ拡張機能に開始が2回届くことがあるので、すでに開いていれば何もしない。
  2. 受け口に届いた通知を、`pi.sendMessage(…, { triggerTurn: true, deliverAs: "followUp" })` で会話に入れる。待機中ならすぐ動き出し、作業中なら作業のあとに処理される。

**受け口の場所**
- Pi のプロセス番号から決める。
  - 拡張機能は、自分のプロセス番号（Pi 本体）を使う。
  - ブリッジは、親のプロセス番号を使う。Pi がブリッジを直接起動するので、両者は一致する。
- Linux・Mac：OS の一時フォルダーの Unix ソケット `catchball-pi-<プロセス番号>.sock`。Windows：名前付きパイプ `\\.\pipe\catchball-pi-<プロセス番号>`。
- そのため、mcp.json の `command` は、ほかの AI と同じく `node` にする（`npx` などを挟むと、親のプロセスが Pi でなくなる）。Node のバージョン管理の道具（Volta など）の中継が挟まる場合は、node の実体の絶対パスを書く。

**流す内容**
- ブリッジから拡張機能への1方向。1行に1つの JSON（`{"content":"<通知文>"}`）。
- 通知文は、ブローカーが作る今の文面（本文なし）をそのまま使う。

**登録のしかた**（ドキュメントに書く）
- `mcp.json` に、session_mail を `command: "node"`・`args: [<ブリッジ>]`・`exposure: "direct"` で書く。
- `exposure: "direct"` は、ツールがモデルに直接見えるようにするための、Pi の設定。Codex の `default_tools_approval_mode` と同じく、登録の設定として書く。

**変えないもの**
- ブローカー・DB・WebUI・管理用 CLI・AI に渡す文面・ツール・設定。

**分かっていて受け入れること**
- WebUI と `status` では、Pi の種類が「Claude」と表示される。
- Pi の `/new`・`/resume`・fork・`/reload` では、Pi がブリッジを起動し直すので、参加していない状態に戻る（未取得は残る）。同じ ID で参加し直せば、通知が再開する。Claude の `/clear` とは違うので、OPERATIONS に書く。

## 5. 試験の決定事項

**良い試験とは**：外から見える動きだけを確かめる。受け口に何が届くか、ブローカーの状態（WebUI の API・`status` に出るもの）がどう変わるか、拡張機能が Pi の API をどう呼ぶか。

**自動試験**
1. **ブリッジ**
   - 今の自動試験の「会話の中から参加」と同じく、試験がブリッジを子プロセスで起動し、接続名 `pi` の MCP クライアントで話す。
   - ブリッジの親は試験のプロセスなので、試験自身が、自分のプロセス番号の受け口を開く。
   - 確かめること：
     - 会話 ID なしで参加できる。
     - 確認用の通知と新着の通知が受け口に届く。
     - 通知に本文が入っていない。
     - `claude/channel` の通知が出ない。
     - 受信すると「確認済み」になる。
     - 受け口が開いていないと、通知が失敗として記録される。
2. **拡張機能**
   - 拡張機能に、Pi の API の偽物（呼ばれ方を記録するだけのもの）を渡して読み込む。
   - 確かめること：
     - セッションの開始で受け口が開く。
     - 届いた通知が、決めた設定で `sendMessage` に渡る。
     - 終了で受け口が閉じる。

**前例**：自動試験の「MCP ブリッジ：8ツール、Claude には channel 通知、Codex には codex queue」「会話の中から参加」。

**実物での試験**
- 実物の Pi 1.5.0（モデルは Haiku。料金を抑えるため）で確かめ、`docs/verification/` に記録する。
- 確かめること：
  - 参加すると「確認済み」になる。
  - 相手から送ると、Pi が自分から受信して返信する。
  - 作業中に届いたものは、作業のあとに処理される。
  - Esc で中断したあとも、再通知で受信される。
  - `/new` のあと、同じ ID で参加し直すと、未取得の通知が届く。

## 6. 対象外

Codex・Claude にない機能は、足しません。

- 拡張機能による session_mail の自動登録や、設定の書き換え。
- 退出・削除の前の確認。Codex・Claude でも、確認はそれぞれの承認の設定によるもので、Catchball の機能ではない。
- WebUI・`status` で「Pi」と表示すること（DB の変更が要るため）。
- `-p`（1回答えて終わる）・JSON・RPC のモード。対象は、Pi のふだんの対話の画面（TUI）で起動したまま待機するセッションだけ（RPC は、実物での試験を自動で進めるために使うだけ）。

## 7. 補足
