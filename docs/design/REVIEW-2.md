## 2. 主要な設計判断の再評価（ADR）

### ADR-001：Codex への受信通知の経路

**Status:** Accepted（確認済み）　**Deciders:** ユーザー、実装担当

**Context**：Codex の既存の TUI セッションへ、外部から「未取得がある」と知らせ、ユーザーが入力しなくてもターンを始めさせたい。仕様書 §10 では `codex queue` を使い、app-server クライアントは後続とすることになっている。

| 選択肢 | 複雑さ | 自動起動 | 既存会話の維持 | 評価 |
|---|---|---|---|---|
| A. `codex queue`（採用） | 低 | ◎ アイドル中なら自動でターンが始まる（ソースで確認） | ◎ | 採用 |
| B. app-server クライアント（`thread/queue/add` を直接呼ぶ） | 中〜高 | ◎ | ◎ | 後続。A がうまくいかない場合の代わり |
| C. Stop フックで受信箱を確認し、ターンの終了を止める | 中 | × アイドル中のセッションは起こせない | ◎ | 補助にしかならない（仕様書 §10 でも不採用） |

**Trade-off**：A は実体が「Codex 側の SQLite キュー」なので、確実に届き、再起動しても消えない。その代わり、別のプロセスから入れたメッセージは10秒ごとのポーリングで拾われ、最大で約10秒遅れる。また、Interrupted の状態では自動で送られない（REVIEW H1）。

**Consequences**：
- やりやすくなること：届いたかどうかの保証を Codex に任せられる。
- 難しくなること：Codex 側のキューに溜まった通知を取り消せない（REVIEW C3 の原因）。
- **今回の新しい指摘 N1**：デーモンが動いていない環境では、`codex queue` が呼ばれるたびに**組み込みの app-server を自分で起動してから終わる**（ソース `tui/src/session_queue_commands.rs`）。通知のたびにプロセスを起動する重さがあり、その組み込みサーバーが MCP サーバー（session_mail のブリッジを含む）まで起動するかどうかも分かっていない。仮に起動すると、トークンのないブリッジが一瞬立ち上がって終わるだけなので害はないが、通知1回に数秒かかる可能性がある。→ スパイク S-1 に「queue 1回の所要時間と、起動される子プロセス」の観測を加える。

### ADR-002：Claude への受信通知の経路

**Status:** Accepted（未検証の点が残る）

| 選択肢 | 複雑さ | Codex も参加できるか | 前提 | 評価 |
|---|---|---|---|---|
| A. 自作 Channel（採用） | 中 | ◎（ブローカーが中継する） | research preview、開発用フラグ、組織の許可 | 採用 |
| B. Claude 標準のセッション間メッセージング | 低 | × Claude 同士だけ | v2.1.224 以降 | 不採用。Codex が参加できず、WebUI にも出ない |
| C. Hooks（Stop など）で受信箱を見る | 中 | — | — | 補助のみ。アイドル中は起こせない |

**Trade-off**：A は preview の機能なので、仕様が変わる・止められるリスクがある。そのため、**A が使えなかったときの代わりの手段を、あらかじめ決めておくべきである**（新しい指摘 N2）。代わりの候補は次の2つ。
- (a) 組織の管理者に Channels を有効にしてもらう
- (b) Claude 側だけ、ブローカーが標準のセッション間メッセージングのソケットへ通知を出す。ただし、このソケットのプロトコルは公開されていないので、MVP では採らない。

現実的な代わりは (a) だけである。したがって、S-4 が不合格なら即座に「最終要件未達・ユーザーと協議」となることを、IMPLEMENTATION_PLAN に明記する。

### ADR-003：送信者を識別する仕組み（セッションごとのトークンファイル）

**Status:** Accepted（REVIEW C2 の修正が前提）

| 選択肢 | なりすましへの強さ | 導入の手間 | 評価 |
|---|---|---|---|
| A. 起動時にトークンファイルのパスを渡す（Codex は `-c`、Claude は環境変数）（採用） | ツール API 経由のなりすましは防げる | 起動スクリプトが必要 | 採用 |
| B. MCP サーバーをセッションごとに別名で5つ登録する | 同じ | 設定が5倍になる。Claude は両方のセッションが両方の設定を読むので、分けられない | 不採用 |
| C. 実行時に会話 ID から自分を特定する（SessionStart フック → ファイル → ブリッジ） | 同じ | 2段階になり、ブリッジの起動との順序の問題がある | 補助（REVIEW M2 の検知用途）として採用 |

**Consequences**：起動スクリプトが運用の要になる。起動スクリプトを使わずに起動するとトークンがなく、ブリッジは「接続設定が未完了」と返す。こうして失敗が表に出るので、仕様の「無断の置き換えをしない」に合っている。

### ADR-004：通知してから本文を取りに行く方式（本文は DB を正とする）

**Status:** Accepted（コンテキスト消費への対策を追加すべき）

| 選択肢 | 確実性 | ターン数・トークン | 仕様書 |
|---|---|---|---|
| A. 通知は件数だけにし、本文は receive で取得する（採用） | ◎ DB が正本 | receive と ack で、最低2回のツール呼び出し | §8 に準拠 |
| B. 通知に本文を入れる | △ Claude は ACK がなく、Codex のキューには本文が残る | 少ない | §8 に反する |

**Trade-off**：A は仕様書のとおりで、正しい選択である。ただし、統括（codex-main）に重さが集中することが見落とされていた（新しい指摘 N3）。
- 担当4名からの報告が、通知1回ごとに codex-main の1ターンになる。
- receive の応答には、毎回、参加者5名の全情報（役割の全文を含む）が付く。
- 本文は最大で 20,000 文字ある。

ユーザーと対話する会話そのもののコンテキストが、早く消費される。

**対策**（仕様書に反しない範囲）：
1. receive の応答に付ける参加者一覧に `members_version` を持たせる。前回の受信から変わっていなければ、ID・表示名・送信可否・配送状態だけの**簡易版**を返し、役割の全文は変化があったときだけ付ける。仕様書 §5 の「名前と役割を含む最新一覧を同梱」との整合が要確認なので、**ユーザーの判断事項**とする。
2. 運用指示に「報告は要点を 1,500 文字以内にし、詳細は成果物のファイルやコミットを示す」と加える。
3. 統括の台帳（LEDGER.md）を「会話の外の記憶」として扱い、長い会話の圧縮（compaction）が起きた後は、台帳から状況を復元するよう指示する。

## 3. 実装プランへの指摘

### P1（重要）：中止か続行かを決める検証を、最初の関門にする

現在の計画は「Phase 0 を Phase 1 と並行して進める」としており、S-1 と S-4 の合否は Phase 2 の直前に分かる。しかし、この2つが不合格ならアーキテクチャ自体を変えることになる（ADR-001・002）。そうなると、それまでに作った Phase 1（全体の約4割）の一部が無駄になる。

**修正**：Phase 0 を**最初の関門（1〜2日）**にする。そのために、スパイク専用の仮実装を用意する（新しい作業 0.1）。

```text
spikes/
├─ stub-channel.ts   # 公式の webhook 例を基にした最小の Channel。POST /notify で channel 通知を出し、
│                    #   ツール ping() が呼ばれたら記録する（Claude のアイドル中の自動起動と、resume との併用の確認＝S-4）
├─ stub-mcp.ts       # Codex 用の最小の MCP。ツール ping() の呼び出しを記録する（環境変数が届くか＝S-2、自動承認＝S-8）
└─ run-queue.ps1     # codex queue の所要時間・終了コードの記録（S-1、N1）
```

Phase 0 の完了条件：「Codex と Claude の両方で、アイドル中の通知 → 承認ダイアログなしでツールが呼ばれる」ことが実機で観測できること。これが満たせない場合は Phase 1 に入らず、ユーザーと協議する。

### P2：Windows 上での試験を Phase 1 の完了条件に入れる

better-sqlite3（ネイティブモジュール）、`execFile` で exe を起動すること、パスの解決は、Windows でだけ壊れやすい。今の計画では、Windows での確認は S-6（環境の確認）だけである。→ Phase 1 の完了条件に「Windows 実機で `npm test` が全件通る」を加える（Q2 の回答が Windows の場合）。

### P3：再起動の手順の食い違い

DESIGN §4.7 では、接続世代が変わるたびに receiver_state が unverified に戻る。一方 OPERATIONS §2.5 は、2回目以降の起動では確認を求めていない。このままでは、毎回の起動後に UI が「自動受信 未確認」のまま残る。
→ どちらかに揃える。
- 案1：起動スクリプトの最後で `doctor --probe` を自動で実行する（推奨）
- 案2：同じ会話 ID のまま再接続した場合は、verified を引き継ぐ

### P4：本番の5セッションを止める時間を見積もる

Phase 4 と Phase 5 では、ユーザーの実際の作業セッションを再開し直す必要がある。計画には、その所要時間も「どの時点で作業を止めるか」も書かれていない。→ Phase 4 の冒頭に「導入の時間帯の合意」と、1セッションあたりの目安（終了・再開・probe で約5分）を加える。

### P5：hook-status が重い（REVIEW H2 の補足）

`PostToolUse` のたびに Node のプロセスが1回起動する。Windows では1回あたり数百ミリ秒かかり、ツールの呼び出しごとに遅れが積み重なる。→ hook-status は、依存のない小さなスクリプトにする（`dist/hook.js`、起動時間 50ms 程度が目標）。matcher で絞れる場合は絞る。S-7 で実測する。

### P6：試験の優先順位

試験はおよそ 80 件あり、網羅的である。一方で、**目的達成試験（Phase 5）を2回以上やり直すことが計画に織り込まれていない**。運用指示の調整には、普通は数回の反復が必要になる。→ Phase 5〜6 に「運用指示の修正 → 再試験」を最低2周見込み、B-08（instructions の原文との一致）をその都度通す。

## 4. 設計への小さな指摘

| ID | 内容 | 修正 |
|---|---|---|
| N4 | ブローカーへの書き込みの頻度が `PRAGMA synchronous=FULL` と合っていない。ハートビートの last_seen_at の更新（5人 × 5秒ごと）まで fsync するのは無駄である | 接続状態はメモリで管理し、状態が切り替わったときだけ DB に書く（ブローカー起動時は全員を offline にする設計なので、メモリ管理で整合する） |
| N5 | `channel_members` が未参加（provisioned）の人も返すため、AI が送れない相手を宛先に選ぶ可能性がある | AI 向けは既定で joined の人だけを返し、`include_inactive: true` のときだけ全員を返す。UI 向けは今のまま全員を返す |
| N6 | 統括が1人しかいないことが単一障害点になる。codex-main が中断・切断されると、担当からの報告が溜まるだけになる | 運用指示の担当向けに「統括が切断中のまま[受領]が返らないときは、作業を続けて報告を溜め、ユーザーに直接知らせる手段はない（WebUI で確認される）」と書いておく。MVP では代理の統括は置かない |
| N7 | `client_message_id` をモデルに一意に作らせると、別の送信で同じ値を使い回した場合に IDEMPOTENCY_CONFLICT になり、送信に失敗する | エラーの hint に「新しい ID で送り直す」と明記する（設計済み）。加えて、運用指示で推奨する ID の形に連番を入れる（例 `<ID>-T03-progress-2`、設計済み）。試験で使い回しの頻度を観測する |
