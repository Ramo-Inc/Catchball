# AI通信チャンネル MVP仕様書

**最終ゴールは、統括AIがユーザーと対話し、担当AIへの仕事の振り分け・進捗管理・調整・結果の取りまとめを通じて、実際に開発を進められることである。通信機能やWebUIを実装し終えただけでは、このゴールを達成したことにはならない。**

版：MVP 1.4 ／ 作成：2026年10月30日 ／ 更新：2026年10月31日

対象：独立した既存のCodex CLI 3セッション＋Claude Code 2セッション。

本書は、先の「五セッション通信基盤 統合仕様書」を、今回のMVP向けに絞り直した実装対象仕様である。旧文書は公式機能の調査資料として残す。MVPの範囲については本書を優先する。システムとWebUIはまだ実装していない。

# 要件定義：このツールを作る目的

## 最優先の完了原則：要件達成をゴールとする

本書の機能一覧は目的を実現する手段であり、機能を埋めること自体を開発の終了条件にしない。参加者一覧、個別送信、ブロードキャスト、WebUIがそれぞれ動作しても、統括AIがそれらを使って担当へ仕事を振り分け、進捗を把握し、問題を調整して開発を前へ進められなければ、目的は未達である。

開発担当セッションは、機能単体の試験に加え、ユーザーからの依頼を起点とする実AIの開発運用を一貫して確認する。機能が揃った時点で作業を終了したり、統括運用をユーザーの手作業へ戻したまま「完成」と報告したりしてはならない。目的との間に不足が見つかった場合は、原因を調べ、実装・接続設定・AIへの運用指示を必要な範囲で修正し、再度運用を確認する。

**「機能実装済み」「技術試験合格」「統括運用検証済み」「最終要件達成」は別の状態として扱う。前の状態を、次の状態の代わりに報告しない。** MVPという名称や将来拡張への対応を、統括運用の確認を省略する理由にしない。小さくするのは実装範囲であり、利用目的への適合確認ではない。

## 背景と現在の課題

ユーザーは現在AIを使って開発しており、ユーザーと対話する統括・管理指揮者のAIセッションが、各担当AIへ仕事を振り分け、進捗を管理しながら開発を進める仕組みを作りたい。初期構成は、統括を担うCodex CLIのメイン1セッション、担当者となるCodex CLIの2セッションとClaude Codeの2セッション、合計5つの独立したセッションである。

それぞれの会話履歴と担当を維持しながら、ユーザーからの要望の整理、担当への依頼、進捗や問題の報告、結果の取りまとめ、次の指示を一連の流れとして扱える環境が必要である。

セッション間に共通の通信路がなければ、あるAIの質問や結果をユーザーが別の端末へコピーし、返答を元の端末へ戻す必要がある。また、各AIからは他に誰が参加していて、何を担当し、どこへ問い合わせればよいかが分からない。ユーザー自身も、複数の端末を追い続けなければ、どのAI間で何が伝わっているのか把握しにくい。

## 実現したい状態

**統括AIがユーザーとコミュニケーションを取り、合意した開発内容を各担当AIへ振り分け、進捗・問題・結果を集約して開発を進める。その仕組みを成立させるため、既存の独立したAIセッションを接続し、ユーザーがやり取りをWebUIで把握できる共通の通信基盤を作る。**

ユーザーの主な対話窓口は統括AIとする。統括AIはユーザーとの対話で目的・要件・優先順位を確認し、参加者の役割に応じて仕事を依頼する。担当AIは進捗、質問、障害、作業結果を統括AIへ返す。統括AIはそれをもとに次の指示や担当間の調整を行い、ユーザーへ状況を報告し、判断が必要な点を確認する。

各セッションは同じチャンネルへ名前と役割を登録する。全員へ伝える方針や変更はブロードキャストし、担当同士でも必要な相談を直接行える。通信の経路を統括AIの中継だけに限定するものではないが、担当の進捗や開発全体の状況を把握する責任は統括AIが持つ。

ユーザーは通信のたびに内容を転記せず、統括AIとの対話を中心に開発を進める。WebUIは、統括AIと各担当AIが何をやり取りしているかをユーザー自身が確認するために用いる。

```text
ユーザー ⇄ 統括AI（Codexメイン）
              ├─ 依頼・指示 ⇄ 進捗・質問・結果：Codex担当A
              ├─ 依頼・指示 ⇄ 進捗・質問・結果：Codex担当B
              ├─ 依頼・指示 ⇄ 進捗・質問・結果：Claude担当A
              └─ 依頼・指示 ⇄ 進捗・質問・結果：Claude担当B

共通チャンネル：参加者・役割の確認、個別送信、全員送信
WebUI：上記のAI間通信をユーザーが確認
```

## 全体構想と通信MVPの関係

最終的な目的は、統括AIによる仕事の振り分けと進捗管理を伴う開発の運営である。今回のMVPでは、その仕組みを組み込む土台として、参加者と役割の把握、双方向の連絡、全員への共有、通信内容の可視化を先に成立させる。

MVPの時点でも、統括AIが通常のメッセージで依頼を送り、担当AIが進捗や結果を返信し、統括AIがそれを受けて開発を進める運用を実際に成立させる。タスクの自動割当エンジンや進捗ボードなどを先に実装することは求めないが、後から統括・管理の仕組みを追加できることは初期設計の前提とする。「後で組み込める設計」だけで目的を達成したとは判定しない。

成果物にはブローカーとWebUIに加え、統括AI・担当AIがこの通信路を使うための必要な接続設定と運用指示を含める。誰へ何を依頼し、何を報告するかをAPIの存在だけに任せない。必要な統括動作が実際に起きるところまで検証する。

そのため、参加者の固定IDと役割、送信元と宛先、メッセージIDと返信先をAPIで取得できるようにし、統括AIからの依頼と担当AIからの報告を追える構造にする。将来、タスクIDや報告種別、タスク状態を構造化して追加する際に、通信路を作り直さず拡張できるようにする。画面操作だけに依存する連携は採用しない。

接続中であることは作業中の証拠ではなく、メッセージの取得ACKは依頼完了の証拠ではない。統括AIの進捗管理は、担当AIが返す進捗・障害・結果の報告に基づいて行う。通信状態と仕事の状態を区別する。

## MVPで満たす利用者要件

1. **既存の作業を続けられること。** 5つの会話と担当を維持し、tmuxへ移行せずに参加できる。導入時の接続設定や同じ会話の再開が必要な場合は明示する。
2. **連絡相手が分かること。** AIとユーザーの両方が、参加者の名前・役割・接続状況・送信可否を確認できる。
3. **直接連絡できること。** どの参加AIからも、特定の相手へ個別送信し、返答を受け取れる。全員向けの共有もできる。
4. **相手の都合と独立して送れること。** 実行中や一時的な切断中でも連絡を保存し、受信可能になった時に取得できる。現在の作業を強制中断しない。
5. **やり取りが見えること。** ユーザーがWebUIから通信本文と宛先別の取得状況を確認でき、送っただけなのか、相手が取得したのかを区別できる。
6. **統括の仕組みに組み込めること。** 統括AIが参加者と役割を取得して依頼を送り、担当AIからの進捗・質問・結果を受け取り、次の指示につなげられる。後続のタスク管理を通信APIの上に追加できる。

## 目的を満たしたと判断する場面

たとえば、ユーザーが統括AIに機能追加を依頼する。統括AIはユーザーと内容を確認した後、実装担当へ作業を、設計レビュアーへ確認を依頼する。担当AIは進捗と問題を統括AIへ報告し、統括AIは必要な調整や追加指示を返す。結果が揃ったら統括AIがユーザーへ報告し、決定事項を全員へ共有する。

ユーザーが担当間の連絡を転記することなく、この依頼・進捗報告・追加指示・結果返却が既存5セッションで成立し、統括AIが報告をもとに次の行動を決め、代表的な開発課題を事前の受入条件まで進められることをMVPの到達点とする。ユーザーはWebUIからその経過を追える。

通信基盤だけであらゆる開発課題の成功やAIの判断品質を保証するものではないが、それは代表的な課題で目的適合を検証しなくてよいという意味ではない。検証した課題と条件、到達した結果、残る制限を示して達成範囲を判断する。

# 1. 作るもの

**AIが同じチャンネルに参加し、誰がいるかを確認し、相手を指定して、または全員へメッセージを送れる。ユーザーはWebUIで参加状況とやり取りの本文を見る。**

最初は1つのチャンネルと5セッションで成立させる。Codexメインは開発上の統括・管理指揮を担う。通信APIの利用権限は他の4セッションと共通で、他セッションの承認を代行する権限は持たない。

AI向けのインターフェースはMCPツール、人間向けはローカルWebUI。この2つが同じ参加者一覧と同じメッセージ履歴を見る。

## MVPの4機能

| 機能 | AI側 | ユーザーのWebUI |
|---|---|---|
| 参加 | 固定の参加者IDに表示名・役割を登録してjoin／leave | 名前・役割・参加・退出を確認 |
| 参加者確認 | 名前、役割、種類、接続、送信可否を取得 | 参加者一覧と役割・状態の理由を表示 |
| 送信 | 個別送信、全員送信 | 誰から誰へ送ったか、本文を確認 |
| 受信 | 通知をきっかけに受信箱から取得 | 宛先ごとの取得状況を確認 |

依頼・進捗報告・質問・結果返却は、まず通常のメッセージで行い、返信にはreply_toを付けて元の依頼と対応付ける。MVPでは専用のタスク管理APIは作らず、後続で追加できる通信契約を維持する。

# 2. 画面で分かること・分からないこと

ユーザーが把握できるのは、**参加者の名前と役割、接続状況、宛先、送受信時刻、通信本文、取得状況**。

各AIの内部推論や、そのAIが端末で読んでいる全ファイル、モデルへ渡った全コンテキストまでは表示しない。作業内容を共有したければ、AI自身がメッセージとして送る。ブラウザーにAIの会話全文や秘密情報を自動収集する機能は持たせない。

個別メッセージは「相手AIだけに配送する」という意味で、監視画面を開くユーザーには内容が見える。同一ユーザーが管理するグループを前提とし、参加AI間の秘密DM機能ではない。WebUIにこの扱いを明記する。

# 3. 代表的な使い方

1. 5セッションが表示名と役割を登録して同じチャンネルへ接続する。
2. 各AIは参加直後に参加者一覧を取得する。自分自身も含めて誰が何を担当しているか分かる。
3. 統括のcodex-mainがユーザーと開発内容を確認し、役割に応じて実装担当と設計レビュー担当へ個別に依頼を送る。
4. 担当AIは受信箱から依頼を取得し、進捗・質問・問題をreply_to付きで統括AIへ報告する。
5. 統括AIは報告を見て進捗を把握し、追加指示や担当間の調整を行う。担当AIは結果を返す。
6. 統括AIは結果をユーザーへ報告し、必要な判断を確認する。方針や決定事項は全員へ送る。
7. WebUIで依頼から報告・追加指示までの通信内容と、宛先別の取得状況を確認する。

この流れをCodex同士、Claude同士、両者の間で同じ操作にする。元の会話IDを維持し、サブエージェント生成や新規会話への無断置換はしない。

## 4.2 参加者欄

表示名の直下に役割を常時表示し、Codex／Claudeの種類、接続中／切断中、受信接続の準備状況を併記する。長い役割は省略し、参加者を選択すると全文と固定IDを確認できる。選択時はその参加者が送信元または宛先に含まれる履歴へ絞り込む。宛先候補にも「表示名 — 役割」を表示し、製品名だけで相手を選ぶ必要がないようにする。

「参加中」と「接続中」は別にする。接続が切れても参加資格は維持し、切断表示に切り替える。明示的なleaveで退出する。色だけで伝えず、状態名と理由を併記する。

AIから見た送信可否と、ユーザーから見た接続状況を同じデータから作る。未準備、承認待ち、切断中の参加者を、すぐに受信できるかのように表示しない。

## 4.3 通信履歴

新着順を固定せず、会話として読める時系列順（古→新）に並べ、初回は直近100件を読み込む。古い履歴は「以前の通信を表示」で取得する。

表示項目は時刻、送信元、宛先（個別名／全員）、本文、取得済み件数。全員送信も投稿は1件として表示し、展開すると各宛先の「未取得／取得済み／退出で配送停止／要確認」が分かる。返信先があれば元投稿へ移動できる。

本文はプレーンテキストとして表示する。HTMLを実行せず、URLも自動で開かない。長文は数行で折り畳み、全文表示できる。改行・日本語を維持する。

## 4.4 状態と例外の見せ方

- 初回の空画面：「まだ通信はありません。AIが参加して送信すると、ここに表示されます。」
- 参加者ゼロ：「参加者はまだいません。」と接続手順への導線。
- WebUIがブローカーに接続できない時：上部に「接続が切れています。表示は最終取得時点です。」と最終更新時刻。
- 全員送信が一部未取得：「3/4取得済み。claude-2は切断中のため待機」。
- AI接続の準備ができていない時：「自動受信は未準備」。接続中の緑表示だけで正常扱いしない。
- 輸送結果が不明な時：「受信を確認できません」。送信成功や取得済みと表示しない。

ユーザーからの本文送信、AIの起動・停止、承認操作、権限変更、グラフや分析ダッシュボードはMVPに入れない。WebUIは観察に必要な操作に限定する。

# 5. AIが使う最小インターフェース

| MCPツール | 用途 | 主な返却値 |
|---|---|---|
| channel_join | 表示名・役割を登録して自分として参加 | channel_id、自分のID・表示名・役割、参加者一覧 |
| channel_members | 今いる相手の担当と送信可否を確認 | 自分を含む一覧、表示名、役割、接続、受付可否、理由 |
| channel_send | 個別または全員送信 | message_id、確定した宛先一覧 |
| channel_receive | 自分宛の未取得本文を取り出す | message_id、送信元、本文、reply_to |
| channel_ack | 本文を取得したことを記録 | message_idと受信者の取得状態 |
| channel_leave | 退出する | 退出結果 |

最小CLIもjoin／members／send／receive／ack／leaveだけを公開し、同じ処理を呼ぶ。導入用のserve／doctorは管理者用コマンドとし、モデルのツールへ公開しない。

### 参加時の名前と役割

channel_joinはdisplay_name（表示名）とrole（このセッションの担当内容）を必須で受け取る。固定のagent_idと元会話IDは認証済みの接続情報から決まり、名前や役割を書き換えても別セッションにはならない。

```json
{
  "display_name": "設計レビュアー",
  "role": "APIとデータ設計のレビュー担当。設計上の相談やレビュー依頼を受け付けます。"
}
```

対応する自作CLIの例：

```powershell
session-mail join --name "設計レビュアー" --role "APIとデータ設計のレビュー担当"
```

表示名は前後の空白を除いて1〜40文字、役割は1〜200文字のプレーンテキスト。同じチャンネルに参加中の表示名は重複を拒否する。役割は自由記述で、同じ担当の参加者が複数いてよい。比較用の表示名はUnicode NFC正規化と英字の大文字小文字を区別しない比較を用いる。空欄や制御文字は入力エラーとし、役割を製品名から推測して埋めない。

役割には「何を担当し、どんな依頼を送る相手か」を書く。初期登録の例は次のとおりで、実際の担当に合わせて変更できる。

| 固定ID | 表示名 | 役割 |
|---|---|---|
| codex-main | 統括・管理指揮 | ユーザーとの対話、仕事の振り分け、進捗管理、担当間の調整、結果の取りまとめ |
| codex-sub1 | 実装担当A | ブローカーと通信APIの実装 |
| codex-sub2 | 実装担当B | WebUIと表示の実装 |
| claude-1 | 設計レビュアー | API・データ設計の相談とレビュー |
| claude-2 | テスト担当 | 動作確認、テスト観点、問題の報告 |

同じ認証済み参加者が再joinした場合は、自分の表示名と役割だけを原子的に更新する。表示名の衝突時は全体を拒否し、以前の登録を維持する。プロフィール更新では接続世代や配送状態を変更せず、重複した参加者も作らない。再接続だけなら登録済みの名前と役割を維持する。更新後の一覧はAIとWebUIの次の取得に反映する。

送信者は役割の説明を見て相手を判断し、実際の送信には一覧が返す固定IDを指定する。役割名への自動ルーティングや、表示名からの曖昧な宛先解決はMVPには追加しない。担当が曖昧なら相手に質問するか全員送信を使える。

roleは担当内容の自己申告であり、承認権限や管理権限を与えるものではない。他の参加者の役割を書き換えたり、本文の指示で送信元を変更したりはできない。

### 参加者一覧の例（自作API）

```json
{
  "channel_id": "dev",
  "self_id": "codex-main",
  "members": [
    {
      "id": "claude-1",
      "display_name": "設計レビュアー",
      "role": "APIとデータ設計のレビュー担当。設計上の相談やレビュー依頼を受け付けます。",
      "provider": "claude",
      "membership": "joined",
      "connection": "online",
      "can_send": true,
      "delivery": "ready"
    },
    {
      "id": "claude-2",
      "display_name": "テスト担当",
      "role": "動作確認、テスト観点、問題の報告を担当します。",
      "provider": "claude",
      "membership": "joined",
      "connection": "offline",
      "can_send": true,
      "delivery": "queued",
      "reason": "切断中。再接続後に配送します"
    }
  ]
}
```

can_sendは「この送信者からメッセージを受け付けられるか」であり、相手が今すぐ作業可能という意味ではない。deliveryはready／queued／unavailable。未参加・退出済み・グループ外はcan_send=false。自分への個別送信も初期版では拒否する。

AIはjoin後、送信前、宛先エラー後にmembersを確認し、名前と役割から依頼先を選ぶ。毎ターンの参加者一斉通知は送らない。本文を受け取る時にも名前と役割を含む最新一覧を同梱し、構成変更や担当変更を把握できるようにする。

### 個別／全員送信の例（自作API）

```json
{"to":"claude-1","body":"この設計を確認してください。","client_message_id":"request-001"}
```

```json
{"to":"all","body":"設計はこの内容で進めます。","client_message_id":"share-001"}
```

fromは接続資格情報からサーバーが決める。モデルは他の送信者を名乗れない。返信は通常のsendに任意のreply_toを付ける。ACKは本文の取得を表し、依頼の完了とは区別する。

# 6. 個別送信・ブロードキャストの厳密な意味

個別送信は、送信時点で同じチャンネルにjoinedの相手1名を指定する。

全員送信は、**送信を受理した瞬間のjoined参加者全員から送信者自身を除いた集合**へ送る。切断中でもjoinedなら含む。未準備の参加者は宛先に含めて保留理由を表示する。参加者が後から増えても過去の全員送信は自動配送しない。

宛先集合をDBに確定してから送信受付を返す。全員送信の再試行は同じ集合を返し、その時点の参加者で再展開しない。宛先ゼロはNO_RECIPIENTSエラーとし、成功投稿を作らない。

明示的なleave後はその相手への新規送信を拒否する。退出者への未取得配送はcancelled_leftとし、履歴からは消さない。同じ参加者が再joinしても取消済み配送は復活させない。単なる切断はleaveではないため、未取得を保持する。

履歴の閲覧はWebUIのユーザーに許可する。各AIが取得できる本文は自分宛のみで、他AI間の個別通信は一覧ツールから取得できない。

# 7. 最小構成

```text
Codex 3セッション ─ MCPブリッジ ─┐
                                ├─ ローカルブローカー ─ SQLite
Claude 2セッション ─ Channel橋 ──┘           │
                                             └─ WebUI

受信通知：ブローカー → Codex queue／Claude Channel → 各セッション
本文取得：各AI → channel_receive → ブローカー
```

ブローカー1プロセスがAPI・静的WebUI配信・DB・通知を担当する。同じローカル接続先を使い、別のフロントエンドサーバーやクラウドサービスは不要とする。WebUIは短い間隔（設計値2秒）で差分取得すれば足りる。初期版ではWebSocketの独自配信基盤を作らない。

保存先は同期フォルダー外のユーザー専用ローカル領域。DBを開くのはブローカーのみ。技術構成は前文書のTypeScript＋公式MCP SDK＋SQLiteを継承するが、具体的な依存版は実装開始時に固定する。

# 8. 必要最低限の保存と信頼性

DBは次の4領域で足りる。

| 領域 | 保存内容 |
|---|---|
| participants | agent_id、display_name、表示名比較キー、role、製品、元会話ID、チャンネル参加、世代、最終接続、受信準備 |
| credentials | agent_id、トークン検証値、失効情報。生トークンは保存しない |
| messages | ID、送信者、個別／全員、本文、作成時刻、返信先、冪等キー、宛先集合 |
| deliveries | message_id＋recipient_id、未取得／取得済み／取消、通知試行と最終結果 |

MVPは1チャンネル固定なので複雑なチャンネル管理テーブルは不要。将来の複数チャンネル対応のためchannel_idは保存する。

参加中の(channel_id, 表示名比較キー)に一意制約を設定する。宛先と送信元の参照は固定agent_idで保持し、役割や表示名を変更しても過去の通信相手は変わらない。履歴には送信時の表示名を保存し、現在の役割は参加者欄で確認する。過去の投稿へ現在の役割を遡って付与しない。

messageと全宛先のdeliveryを1回のトランザクションで永続化してから「受付済み」を返す。送信者＋client_message_idに一意制約を置き、同じ内容の再送は同じ結果を返す。異なる内容で同じキーを使うと競合エラー。

receiveは未ACKの本文を返す。ACK応答が失われても同じmessage_idで再ACKできる。取得後に落ちた場合は再取得され得るため、AIは同じIDの依頼を二重処理しないよう扱う。外部の仕事まで厳密に1回にする保証はしない。

UIには「受付済み／未取得／取得済み」を表示し、輸送の成功を取得済みへ変換しない。業務のprocessing／completed、task_key、詳細な処理lease、分散トランザクションはMVPでは扱わない。

通知は未取得があることだけを伝え、本文の正本はDBとする。通常時は初回通知、再接続時の通知、未取得が残る場合の間隔を空けた再通知で足りる。通知の連打を避け、同じ宛先の複数未読を1通知へまとめる。停止や承認待ちが分かる場合は新規通知を保留する。

通知の記録前後にプロセスが落ちると重複通知が起こり得るが、IDで同じ本文と識別できる。再起動後に未取得を走査し、接続復旧時に再通知する。取得済みの自動再送は行わない。

# 9. 接続状態と権限

参加、接続、自動受信準備を別々に保存する。定期的な接続確認はAIモデルではなくブリッジが送る。設計値として5秒間隔、30秒間更新がなければ切断表示にする。AIが考えているかはheartbeatから判定しない。

| 相手の状態 | 送信受付 | 受信・UI |
|---|---|---|
| アイドル・受信準備済み | 可 | 通常通知、取得ACK待ち |
| 実行中 | 可 | 公式キューへ通知。現在の仕事を中断しない |
| 切断中・参加維持 | 可 | 未取得として保持し、再接続後に通知 |
| 承認待ちと判明 | 可 | 保留と表示。メッセージで承認しない |
| 接続中だが自動受信未準備 | 可 | 保留理由を表示。正常配送と扱わない |
| 未参加・退出済み | 不可 | 宛先候補から送信不可と返す |

正確な実行中・承認待ちを観測できない接続では「不明」と表示し、推測で埋めない。MVPで高度な状態推定を追加しなくても、参加・接続・受付可否は一貫して分かるようにする。

通信の基盤は127.0.0.1へ限定する。AIごとに別の資格情報を発行し、グループ外送信、他人のACK、送信元詐称を拒否する。WebUIは同じユーザーが読むための別資格情報で認証する。秘密をURL、ログ、メッセージ本文に含めない。本文をHTMLとして実行しない。

WebUIは資格情報を端末内で入力するローカルの認証画面を持ち、認証情報をURLへ埋め込まない。HTTP側はOrigin／Host検証を行う。AIの権限を変更する操作や承認の代行は公開しない。

# 10. 公式受信経路の扱い

先の文書で確認した2026年10月30日時点の資料に基づく。今回の範囲変更に合わせ、実装経路を次に固定する。

- Codexは公式queueを受信通知に使い、送信と本文取得は共通MCPで行う。
- Claudeは公式Channelで受信通知を受け、同じMCPサーバーのツールで送信と本文取得を行う。
- Channelの通知にネイティブACKがないため、channel_ackを残す。
- app-server専用クライアントとSocketアダプターはMVPに含めない。
- Hooksだけで任意のセッションを確実に起こせるとは扱わない。
- 既存の会話へ接続設定が必要。Channelを読み込むための同一会話の再開が必要な場合がある。「起動済みプロセスへ無条件に後付け可能」とはしない。

テスト用セッションで自動受信を確認してから、既存5会話へ導入する。ダミー参加者とブラウザーだけで動くデモは、AI間通信の完成と区別する。

# 11. 最小APIと開発順序

WebUI用はGET /api/members（固定ID・表示名・役割・接続・送信可否を含む）、GET /api/messages（cursor・参加者・種別・検索語）、GET /api/messages/{id}/deliveries。初回はページング取得し、以後は増分を取得する。ACKによる既存投稿の更新も取りこぼさないよう、増分カーソルはmessage_idではなく変更連番を使う。接続状態と名前・役割は参加者APIを再取得する。

AI向けはjoin、members、send、receive、ack、leave。CLI・MCPの両方から同じ認証・業務処理を呼ぶ。WebUIに業務送信用APIを追加する必要はない。

1. ブローカー、参加者一覧、個別／全員送信、SQLite、取得ACKを作る。
2. MCPツールと実際のCodex／Claude受信通知を接続し、2セッションで往復させる。
3. 同じデータを表示するWebUIを作る。
4. 既存5会話で参加・全20方向・全員送信・切断復旧を確認する。
5. 接続設定と統括・担当それぞれの運用指示を揃え、代表的な開発課題で「ユーザーとの対話→振り分け→進捗把握→調整→成果確認→報告」を実際に行う。
6. 機能試験は合格でも運用が成立しない箇所を修正し、再検証する。最終要件に対する証拠と未達項目を揃えて完了を判断する。

UIとダミー通信だけを先に完成扱いせず、公式受信経路の往復を早い段階で確認する。

# 12. MVPの受入基準

## 12.1 機能の成立条件

以下の機能試験は必要条件であり、この表の合格だけでは開発完了にならない。12.2の目的達成試験と12.3の完了判定も満たすこと。

| 試験 | 完了条件 |
|---|---|
| 名前・役割で参加 | joinで名前と役割を登録し、各AIとWebUIが同じ5名の固定ID・名前・役割を取得できる |
| 統括運用への接続 | 統括AIからの依頼、担当AIからの進捗・質問・結果、統括AIからの追加指示を元の依頼と対応付け、APIとWebUIで追える |
| 役割で相手を選ぶ | 「設計レビュー依頼」を役割の説明から選んだclaude-1の固定IDへ送信できる |
| 登録の更新と衝突 | 自分の再joinで役割を更新でき、重複名や空欄は拒否。ID・過去履歴・未取得配送は維持される |
| 個別送信 | 全20方向に送信・本文取得でき、他のAIの受信箱へ混入しない |
| 全員送信 | 送信者以外の4名へ届け、UIでは投稿1件・宛先4件と分かる |
| 宛先の確定 | 再送や途中joinで過去の全員送信の宛先が増減しない |
| 自動受信 | アイドル時にユーザーの追加入力なしでreceiveとACKまで到達する |
| 実行中 | 元の仕事を中断せず、処理可能になった後に取得できる |
| 切断 | 一人が切断しても他は通信可能。再接続で未取得を受け取れる |
| 承認 | メッセージで承認待ちを突破せず、未取得と保留理由が分かる |
| WebUIの可読性 | 参加者名の下に役割があり、送信元・個別／全員・本文・時刻・宛先別取得が読み取れる |
| 表示の鮮度 | WebUI切断時に古い表示と分かり、再接続で追いつく |
| 退出 | 以後の新規配送から外れ、過去履歴と取消理由は残る |
| 再送・再起動 | 同じキーで投稿が増えず、永続受付済み投稿を失わない |
| 権限 | 偽from、他人ACK、認証なし、HTML本文によるスクリプト実行を拒否 |

機能の技術試験は、ユニット（宛先展開と重複）、DB（再起動）、API（権限）、実AI（20方向）、UI（本文・取得状況・切断表示）に絞る。それに加え、次の目的達成試験で、実際の統括運用と開発成果を確認する。

## 12.2 最終要件に対する目的達成試験

事前に小規模な開発課題と成果物の受入条件を具体的に定め、実際のCodex 3セッション・Claude 2セッションで以下を通して実行する。通信実演用の定型文を交換するだけのシナリオは合格にしない。検証中に、都合のよい条件へ一方的に変更して合格扱いすることも認めない。

| 検証段階 | 観測する結果・証拠 |
|---|---|
| ユーザーとの対話 | 統括AIが目的・要件・受入条件を確認し、担当への依頼へ落とし込む |
| 仕事の振り分け | 名前と役割に基づいて4担当へ意味のある作業を依頼し、担当・期待結果が通信履歴から分かる |
| 進捗の把握 | 担当から進捗・質問・障害の報告を受け、統括AIが着手済み・待機・未解決を把握する。ACKだけで完了扱いしない |
| 調整と追加指示 | 検証課題に含めた仕様確認やレビュー指摘に対し、統括AIが回答・方針確認・追加指示を行い、担当が作業を継続する |
| 成果の確認 | 統括AIが担当の完了宣言だけで閉じず、成果物とテスト・レビュー結果を受入条件に照らして確認し、不足があれば修正を依頼する |
| ユーザーへの報告 | 統括AIが達成結果・検証結果・残課題をまとめて報告する。ユーザーが各担当の履歴を手で集計する必要がない |
| ユーザーからの可視性 | WebUIで依頼・報告・追加指示・結果の本文と対応関係を追え、統括AIの報告の根拠を確認できる |
| 継続して利用できること | 続く修正または追加依頼でも、既存会話と役割を保ったまま同じ運用を繰り返せる。担当への再配布や起動のために毎回ユーザーの伝言を必要としない |

人間が行う要件の判断や必要な承認は、この運用に含まれる。担当間の転記・配送・報告の集約を人間が肩代わりする場合は、肩代わりした箇所を未達として扱う。外部制約で試験を実行できなければ「未検証」であり、ダミー通信の結果で代替しない。

証跡には、課題と受入条件、使用したCLI版と会話の識別情報、担当ごとの依頼、進捗・問題報告、統括AIの調整、成果物、検証結果、対応するメッセージIDを残す。単一の送信成功や画面のスクリーンショットだけを目的達成の証拠にしない。

## 12.3 開発を終了してよい条件と未達時の扱い

開発完了の判断には、機能試験の合格、実5セッションでの目的達成試験の合格、運用に必要な接続設定・指示・再開手順の提供がすべて必要である。結果は「どの要件を、どの操作と成果物で確認したか」が分かる形で報告する。

機能試験のみ合格なら「機能実装済み・統括運用は未検証」、運用上の問題が残るなら「最終要件未達」と明記する。通信APIを渡して『あとはユーザーが運用してください』とすることや、モデルの振る舞い・接続設定を一律に範囲外として切り離すことで、最終ゴールを達成した扱いにしてはならない。

未達が分かったら、開発担当は目的に戻って原因を切り分け、必要な修正と再試験を続ける。外部制約やユーザー判断が必要で進められない場合は、その理由、未達要件、再現手順、次に必要な対応を具体的に残す。セッションの交代や中断は開発完了ではなく、未解決事項を引き継ぐための区切りとして扱う。

MVPで後回しにする機能があっても、本書の目的達成を妨げる不足まで後回しにして完了とはしない。範囲の見直しが必要なら、機能の有無ではなく、目的への影響と代替方法を示してユーザーと調整する。

# 13. MVPから外すもの

複数チャンネルの作成・管理、グループ間ルーティング、役割権限の細分化、専用のタスク割当エンジン・進捗管理画面・自動完了判定、添付ファイル、遠隔PC、クラウド公開、WebUIからのAI操作、詳細な監視分析、Socket／app-serverの交換、厳密な1回の業務実行は後続とする。統括AIによるメッセージベースの依頼・進捗把握はMVPで可能にし、専用機能の追加を妨げない。

ただし、送信先を間違えないこと、本文の永続化、重複識別、取得ACK、最低限の認証は通信路を成立させるためMVPにも残す。

本節で後続とした専用機能は、目的達成のための実装方法を小さくするための区分である。統括AIによる仕事の振り分け・進捗把握・調整そのものや、その実運用の確認を後続へ送るものではない。
